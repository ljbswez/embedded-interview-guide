# 现场调试与证据链

面对崩溃、卡死、抖动和丢包，用分层假设、有限观测及可复现测试定位首次失效。

适用方向：MCU / RTOS 与嵌入式 Linux。难度标签是复习分层，问题为原创训练题，不代表公司实际面试题。

---

## DBG-01 · 设备几天才崩一次，拿不到稳定复现时怎样开始？

方向：MCU / Linux；难度：深入；关键词：偶发崩溃、证据链、现场保全

### 面试官可能这样问

客户说设备运行三天会重启，实验室暂时复现不了。第一天你做什么，下一版诊断固件放什么，怎样避免收集一堆没用日志？

### 考查意图

把模糊症状变成可分类事件，建立固件身份、触发上下文和第一失败点之间的因果联系。

### 30—60秒口述参考

我先区分是异常复位、看门狗、掉电、进程退出还是业务重连，保留固件与硬件版本、复位原因和发生前负载。下一步加有界事件记录和最小故障现场，让每条假设都有能支持或否定的证据。MCU 保存可信的异常状态与栈信息，Linux 收集匹配符号的崩溃转储和各线程现场。先提高问题可观测性，再缩小触发条件，不先承诺“加日志下次一定抓到”。

### 先把“重启”拆成不同事件

询问是启动标识变化、连接断开还是屏幕卡住，读取平台提供的复位来源并确认标志是否可能残留。建立时间线：固件标识、启动次数、运行时长、温度电源条件、连接数、最近状态转换和最后成功进度。多个客户版本不可混在同一统计里，某地址必须对应准确 ELF；只有源码版本但工具链和链接配置不同，也可能无法可靠还原。

### 记录最后有限窗口与原始现场

用固定容量环形事件区记录事件编号、单调时间戳和少量数值，注明覆盖或丢失计数；严重故障时冻结或复制最近窗口。异常处理尽量不依赖已损坏堆、锁和中断输出。Linux 转储中先看信号、寄存器和线程，再看业务对象；MCU 先验证异常帧可读和架构类型。指针看似合理也可能指向已复用对象，原始值与有效性条件都应保留。

### 每次诊断改动都对应一个判断

例如假设“断线取消后仍有回调”，就记录对象代际编号、取消提交、回调进入和释放四类事件；若假设供电波动，则需要与软件日志独立的电源测量证据。不要同时改十处业务逻辑后宣布不再崩溃。日志还会改变时序和栈，应比较启用前后的资源与延迟，并采用可回滚的小范围插桩。

```text
info files
info registers
info threads
thread apply all bt full
# 在已加载匹配可执行文件和本地转储的 GDB 会话中读取。
```

### 连续追问

**1. 现场没有完整 core dump 怎么办？**

先收最小但可信的证据：固件身份、故障分类、关键寄存器、受界限保护的栈片段与最近事件。随后按最有区分力的假设增加字段，不应为了完整性强读无效地址或耗尽保留空间。

**2. 日志最后一条就是出错位置吗？**

未必，异步日志可能尚未刷出，多线程输出顺序也不必等于事件发生顺序。要区分生成时间和输出时间，使用统一时钟与序号，并记录日志丢弃情况；最后可见记录只能说明某条路径曾到达。

**3. 抓到几次相同栈就能结案吗？**

相同栈能帮助聚类，但可能都是同一个受害者。还需解释哪一次非法状态产生、为何它导致这个崩溃，以及修复如何阻断因果链；最后用原触发序列和相邻场景回归。

### 容易答错的地方

- 把复位都归因看门狗：供电、软件复位、异常升级与进程重启需要不同证据。
- 用不断追加的大日志换取安心：可能改变故障时序并吃掉本来就紧张的资源。

### 动手验证

为“断线后偶发重启”设计不超过十种事件编号，列每条假设的支持证据、反证和下次只改一个变量的实验；说明现场版本如何与符号文件对应。

### 查阅依据

- [GDB: Backtraces](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Backtrace.html)
- [GDB: Debugging Programs with Multiple Threads](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Threads.html)
- [Zephyr: Logging](https://docs.zephyrproject.org/latest/services/logging/index.html)

## DBG-02 · 只有 Release 出错，怎样一步步缩小到真正的配置或代码原因？

方向：通用 / MCU / Linux；难度：深入；关键词：Release故障、差分实验、回归定位

### 面试官可能这样问

关闭优化就不崩，加一行打印也不崩。你会如何安排实验，什么证据才足以怀疑编译器缺陷？

### 考查意图

在保持复现条件的同时构造可比较版本，区分优化、配置、时序和未定义行为。

### 30—60秒口述参考

我先固定失败镜像和输入，把两种构建的宏、链接库、断言、LTO、栈配置与优化选项完整差分，而不只比较 -O。按风险逐项做单变量实验，并保留发布级优化下的符号和反汇编。优先查未初始化、越界、数据竞争及依赖调试副作用的代码。若排除语言和接口错误，才能用最小复现、固定工具链与明确期望语义讨论编译器问题；关优化只是定位手段。

### 先排除其实不是优化的问题

Release 可能定义 NDEBUG，让 assert 中的表达式根本不执行；若代码把初始化或写寄存器放进断言，就会产生业务差异。还可能使用不同栈大小、日志模式、库规格和功能宏。用预处理输出、完整链接命令与构建清单逐项比对，验证差异真的只剩一个假设；不要在“Debug 正常”这个标签上做因果推理。

### 建立一张小而有判别力的实验矩阵

保留原失败配置，另做同优化加符号、单文件降优化、启用对应消毒器、固定调度输入等对照。每个结果都记录复现率、运行时长和资源变化，避免把偶发问题的一次通过当结论。ASan/UBSan 适合定位可执行到的访问或语义问题，TSan 用于支持平台上的线程竞争诊断；它们是不同构建方案，并非所有工具可叠在同一二进制上。

### 从最早坏版本和最小代码同时收敛

若有明确曾正常版本，可以使用 Git bisect 寻找首次出现回归的提交，但前提是判断脚本足够稳定；无法编译或测试条件不满足的版本要标不可判定。定位到提交只说明变化相关，还需继续缩减到导致非法访问或错误假设的最小代码。发布版栈和指令映射可辅助解释变量被优化掉的原因，不能只靠源码单步窗口。

### 连续追问

**1. 把变量都改 volatile 是合理修复吗？**

只有确实需要实现规定的可观察访问时才合理。它不能修复线程数据竞争、对象过期或数组越界，还会改变代码生成并掩盖现象。应要求解释具体错误路径以及为什么选定同步或生命周期修复足够。

**2. 偶发问题怎么做二分？**

给每个候选版本一致的样本、负载、时长和判定阈值，区分失败、暂未复现与无法测试。复现概率过低时先提高触发稳定性；盲把一次没崩标成好版本，会让二分落到错误提交。

**3. 怎样提交可信的编译器 bug？**

保留尽可能小的源文件或预处理文件、工具链版本、目标选项、实际输出和语言层预期，并说明已经排除 UB。两个优化级别结果不同本身还不够，输入也必须位于代码宣称的合法范围。

### 容易答错的地方

- 只比较 -O0 与 -O2，漏掉 NDEBUG、库、宏和链接布局的业务差异。
- 把降低优化后的稳定版本直接发布并停止调查：可能只是时序窗口变小。

### 动手验证

给一段仅发布版失败的假设程序设计四个对照构建，写出每个实验能区分什么；再写一个三态的版本判定规则，避免把无法测试当通过。

### 查阅依据

- [GDB: Debugging Optimized Code](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Optimized-Code.html)
- [Clang: UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)
- [Clang: ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html)
- [Git: git-bisect Documentation](https://git-scm.com/docs/git-bisect)

## DBG-03 · 设备卡死或 CPU 100%，怎样区分死锁、活锁、忙等与中断风暴？

方向：MCU / Linux；难度：深入；关键词：卡死、线程状态、进度诊断

### 面试官可能这样问

业务没有响应，但 CPU 可能很高也可能很低。你第一次抓现场应该看什么，为什么只看一个线程栈不够？

### 考查意图

按执行状态与进度拆分故障类别，用时间序列验证等待关系而不是凭单次快照命名。

### 30—60秒口述参考

我先确认是整机、进程还是单个功能失去进度，再看 CPU 统计口径、线程状态和中断活动。低 CPU 可能是互锁或等待永不满足的事件，高 CPU 可能是忙等、活锁、异常重试或中断风暴。抓所有相关线程与锁的持有等待关系，隔一段时间重复采样，再用进度计数判断是否只是很慢。MCU 同时检查当前异常、屏蔽状态和任务调度，不能只盯主循环。

### 先定义正常进度的可观测条件

业务无响应不等于 CPU 停止。为消息接收、任务执行和输出完成设置单调计数，比较哪个阶段停住；看门狗应关注真正关键任务进度，而不是任意定时中断仍在喂狗。Linux 的百分比可能按单核或整机归一化，一条线程占满一核不能自动解释为所有核耗尽。还要区分用户态时间、内核态时间与可运行却迟迟没被调度。

### 把等待图与重复栈组合起来

一次 backtrace 看到线程等待锁很常见，并不能证明死锁。要找谁持锁、持锁者又等待什么，是否形成环，或者事件生产者已经退出。重复采样若同一组等待关系稳定且没有进度，证据更强；若栈不断变化却只在重试和回退，可能是活锁。回调自注销等待自身结束、锁内调用可重入上层函数都是值得验证的具体假设。

### MCU 还要查中断与临界区状态

某外设标志未按要求清除会不断进入 ISR，使任务饥饿；中断被长期屏蔽则可能让超时、DMA 完成或调度无法发生。读取当前异常与 pending、外设状态并结合 GPIO 或追踪计数判断，注意某些状态寄存器读本身有副作用。不要在活跃系统随意单步依赖实时外设的代码，然后把调试暂停产生的超时当原始故障。

### 连续追问

**1. CPU 很低能排除逻辑错误吗？**

不能，线程可能都在等一个没人再发送的事件，或者等待条件被错误清掉。要沿生产者—通知—等待者链路验证每个状态变化，CPU 空闲只描述调度现象，不说明业务协议正确。

**2. 加 sleep 能修忙等吗？**

它可能降低占用，但若没有正确的等待通知或退出条件，功能仍会卡住且响应变慢。应根据需求改阻塞等待、条件变量或有期限重试，并处理超时和取消；休眠长度不是同步证明。

**3. 死锁修复怎样验证？**

保存可复现的锁顺序和触发交错，统一加锁顺序或改变调用边界后重新跑该交错，并检查正常负载、取消和超时。只把 mutex 改成递归锁可能掩盖设计错误，还需确认共享状态是否允许重入。

### 容易答错的地方

- 所有卡死都叫死锁：忙等、饥饿、中断风暴和丢通知的证据不同。
- 只抓当前线程就下结论：真正持锁者、生产者或高优先级任务可能在其他上下文。

### 动手验证

给两个线程和一个完成中断画等待关系，设计三次间隔采样要记录的指标；分别写出死锁、忙等和中断风暴时预期看到的差别。

### 查阅依据

- [GDB: Debugging Programs with Multiple Threads](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Threads.html)
- [Linux kernel documentation: ftrace — Function Tracer](https://docs.kernel.org/trace/ftrace.html)
- [ST PM0214 Rev 10: STM32 Cortex-M4 MCUs and MPUs programming manual](https://www.st.com/resource/en/programming_manual/pm0214-stm32-cortexm4-mcus-and-mpus-programming-manual-stmicroelectronics.pdf)

## DBG-04 · 平均延迟很好但偶尔超时，怎样测量时延抖动并找到来源？

方向：MCU / Linux；难度：深入；关键词：时延、抖动、trace

### 面试官可能这样问

任务通常一毫秒完成，但偶尔超过十毫秒。你怎样证明延迟发生在哪一段，怎样避免测量代码本身制造尖峰？

### 考查意图

明确端到端指标、时钟和采样边界，将排队、调度、执行与设备等待分解成证据。

### 30—60秒口述参考

我先定义从哪个事件到哪个事件算延迟，把排队、唤醒、真正获得 CPU、执行和 I/O 完成分开打点，用一致单调时钟记录分布、分位数与观察到的最大值。MCU 可用硬件计数器和 GPIO 配合仪器，Linux 可用合适的调度与延迟追踪。保留尖峰附近窗口，并量化插桩开销。平均值不能代替尾部，测试最大值也不是已经证明的最坏执行时间上界。

### 先消除指标和时钟的歧义

请求到达驱动、进入队列、任务被唤醒和实际开始运行是不同时间点。若只在函数首尾计时，会漏掉最严重的排队或调度延迟。时间源要确认分辨率、频率变化、计数回绕、跨核可比较性以及休眠时是否继续计时；墙钟校时会改变日期时间，不适合直接测短区间。日志输出时间也不能替代事件发生时间。

### 分层追踪尖峰而不铺满日志

MCU 可在入口和出口翻转独立 GPIO，用逻辑分析仪观察与中断、外设完成的关系；支持的周期计数器也需确认启用与频率条件。Linux 的 timerlat 可帮助区分计时中断与线程层延迟，ftrace 的调度和相关事件用于追来源，工具可用性取决于内核配置和权限。只启用需要的事件并设置有限窗口，记录丢事件信息，避免追踪本身耗尽缓冲区。

### 用单变量负载验证具体假设

若怀疑长临界区，就将尖峰与关中断或不可抢占区间关联；怀疑存储写入，就观察 I/O 队列及完成；怀疑 CPU 频率或缓存，就固定相应条件做对照。分别测试空载、代表负载、突发和长期压力，并报告样本数、环境与尾部统计。关闭所有后台活动得到的最好成绩只能描述那个条件，不能直接用作生产保证。

### 连续追问

**1. 测出 P99 就足以保证硬实时吗？**

不够，分位数允许一部分样本更慢，硬实时约束关心截止期是否始终满足。测试分布能发现问题和比较方案，但上界保证还需要任务模型、资源阻塞与最坏情况分析等证据。

**2. 为什么 printf 测时常不可信？**

格式化、锁、缓冲和输出带宽都会影响路径，异步日志又会延迟实际输出。可以先记录二进制时间戳到有界区，事后再格式化，并用空测量对照估计打点成本。

**3. 观测不到丢事件能否说明没有尖峰？**

不能。追踪窗口可能没覆盖、缓冲区可能覆盖旧数据、计时源也可能在休眠中停走。应保存事件计数和溢出状态，确认采样完整性，再解释“本次测试未观察到”的范围。

### 容易答错的地方

- 只报告平均值或最小值来回答尾延迟：会隐藏最影响可靠性的少数尖峰。
- 把有限测试观察到的最大值写成绝对最坏上界：样本与证明的含义不同。

### 动手验证

为接收数据到控制输出画五个时间点，说明每段可能的阻塞者；设计正常与突发两组测量，报告计时源、采样数、分位数、最大观测值和丢事件数。

### 查阅依据

- [Linux kernel documentation: Timerlat tracer](https://docs.kernel.org/trace/timerlat-tracer.html)
- [Linux kernel documentation: OSNOISE Tracer](https://docs.kernel.org/trace/osnoise-tracer.html)
- [Linux kernel documentation: ftrace — Function Tracer](https://docs.kernel.org/trace/ftrace.html)
- [Zephyr: Logging](https://docs.zephyrproject.org/latest/services/logging/index.html)

## DBG-05 · 内存问题线索很多，如何从现场地址找到首次破坏或真正遗失的对象？

方向：MCU / Linux；难度：深入；关键词：内存追踪、观察点、对象代际

### 面试官可能这样问

你只知道某个结构体指针偶尔变成奇怪值，另一个版本则运行久了申请失败。怎样安排调查，避免把两种问题混在一起？

### 考查意图

根据空间破坏与生命周期增长建立两条诊断路径，用对象标识、分配记录和最小观测缩小时间窗。

### 30—60秒口述参考

我先分流：地址或字段被改坏，重点找第一次非法写；活跃占用持续增加，重点找所有权结束后仍未回收的对象。前者从受害地址反推分配区间与写入者，用有限观察点或消毒器；后者按业务周期和申请点记录净增长，并区分缓存与分配器保留。两条调查都记录对象代际和固件身份，最后回到具体越界、取消、引用或错误清理路径，而不是只替换分配器。

### 把受害地址放回对象时间线

同一个数值地址可能先后属于不同对象，单记指针不够。记录分配编号、地址范围、大小、所有者和释放时点，发现损坏时判断它是在当前生命周期内还是旧回调访问新对象。若是某字段先正常后异常，缩小到两次有效检查之间，再监测最可能的写入地址。对 DMA 等非 CPU 写入者，普通 CPU 硬件观察点不一定能看到，需核对目标调试设施。

### 用工具找到第一次违约

支持环境中的 ASan 报告可连接访问点、申请点和释放点；GDB watchpoint 可在已知字段变化时停下，但硬件槽位、宽度和地址约束有限，退化软件观察点可能大幅改变时序。先监测一个有区分力的字段，别试图监视整个堆。插桩不能覆盖的库或设备路径要用边界哨兵、受控替身与独立输入输出记录补足。

### 增长调查则做周期账本与失败注入

选一个能够回到相同业务状态的周期，例如连接、收发、取消、断开，结束时比较活跃对象和字节。按分配点聚类找净增量，再让第一个、第二个等申请点依次失败，检查逆序清理是否完整。LSan 对不可达分配的报告有帮助，但仍可达的无界缓存需要业务规则判断。修复后同时测无增长与无提前释放，避免泄漏修成 UAF。

### 连续追问

**1. 观察点从没命中但值变了，能排除 CPU 写吗？**

不能立即排除。可能地址已经换代、观察点未成功插入、访问宽度或资源限制不满足，也可能多线程软件观察点覆盖不足。先确认调试器明确报告的观察方式和覆盖范围，再检查 DMA 等其他写入源。

**2. 为什么给块头加日志后问题消失？**

元数据和打印改变布局、分配重用及执行时序，可能把越界目标挪走。保留原始布局对照，尽量使用外部固定大小账本或采样事件，不把插桩后的稳定当作修复结果。

**3. 怎样验证内存池释放路径？**

除正常释放外，要测试重复归还、外来地址、错池释放和取消后迟到归还，检查接口是否拒绝并保持池结构不变。诊断构建可加代际或使用状态，但不能靠读取已经非法的指针来保证安全。

### 容易答错的地方

- 把每个异常地址都称为野指针而不记录来源：无法区分越界、过期引用和合法对象被破坏。
- 只确认“剩余内存不再下降”就验收：可能通过过早释放换来更隐蔽的并发损坏。

### 动手验证

制作一份十条以内的分配与回调事件记录，包含地址复用，手工判定哪条访问越过生命周期；再列出能区分泄漏与碎片的最少统计指标。

## DBG-06 · 串口偶发丢包，怎样从电气层一路定位到应用协议？

方向：MCU / Linux；难度：进阶；关键词：UART、丢包、吞吐预算

### 面试官可能这样问

低波特率正常，高波特率或压力下偶发丢帧。你会先增大缓冲区吗？怎样知道字节丢在线上、FIFO、DMA、队列还是协议解析？

### 考查意图

分层建立守恒计数与时间预算，把物理错误、驱动溢出和应用帧边界问题分别验证。

### 30—60秒口述参考

我先核对电平、连线和双方串口参数，再用已知序列与外部采样确认线上字节。沿硬件错误、FIFO/DMA 接收量、软件入队出队量和协议校验分别计数，找到第一处不一致。根据波特率算最坏服务间隔与缓存需求，检查中断屏蔽、DMA 缓冲归还、流控和消费者阻塞。串口只提供字节流，一次回调或 read 的边界不等于业务帧；单纯扩容可能只推迟丢包。

### 先验证链路基本事实

确认 TTL 电平与转换器类型、共地、接收发送连接、波特率、数据位、校验和停止位，并测实际时钟误差及信号质量。用递增序号与已知校验的测试流定位缺失位置，比只发送可读文字更容易发现重复和错序。帧错误、奇偶错误、硬件 overrun 与软件缓冲满分别统计；某些状态位读取或清除有规定顺序，要查目标 UART 文档。

### 算出有限缓冲能容忍多久

以 115200 波特、8N1、无额外间隔为例，每字节占十个位，理想数据上限是每秒 11520 字节；消费者完全停二十毫秒会积累约二百三十一字节，还未计突发与余量。若软件区只有六十四字节，加一点任务优先级不能替代容量和服务时间证明。硬件流控能减少溢出风险，但双方支持、响应延迟与剩余空间也需设计。

### 把接收接口语义与帧解析解耦

轮询、中断和异步 DMA API 的缓冲区生命周期不同，不能在驱动仍持有缓冲区时复用或释放。Zephyr 等系统对同一外设的 API 组合有明确约束，应核对所用版本；Linux 用户态还需确认 termios、读取模式和用户缓冲处理。空闲检测或一次 read 可截断一帧，也可合并多帧；解析器应保存跨块状态，用长度、分隔符或校验建立业务边界。

### 连续追问

**1. 打开串口日志后丢得更严重说明什么？**

日志可能共用端口、阻塞消费者、加长 ISR 或竞争锁，从而扩大接收间隔。应使用独立观测通道或只记录有界计数，比较日志开启前后的服务时长，不能据此直接判硬件不稳定。

**2. DMA 已经接收就不会丢了吗？**

仍可能因为缓冲区未及时续接、环形读指针错误、缓存不一致、总线争用或应用消费不及而丢。要分别统计硬件写入、通知到达、软件读取与归还，验证每一段都有明确容量和所有权。

**3. CRC 错误能准确定位物理层吗？**

只能说明校验范围内的数据与预期不一致，软件拼帧错误、覆盖和长度解释错误同样会造成 CRC 失败。把线上采样、驱动原始字节与应用输入按序号对齐，找到第一次差异才有定位价值。

### 容易答错的地方

- 把一次接收回调当完整一帧：压力和驱动分块变化会暴露解析错误。
- 不断增大缓冲却不限制积压或检查服务上界：无限持续超载仍然会丢。

### 动手验证

为 115200/8N1 链路计算五、二十、一百毫秒阻塞所需容量；设计硬件接收、驱动出队和协议接受三层计数，使一次丢包能归到首个差异层。

### 查阅依据

- [Zephyr: Universal Asynchronous Receiver-Transmitter (UART)](https://docs.zephyrproject.org/latest/hardware/peripherals/uart.html)
- [Zephyr API: UART](https://docs.zephyrproject.org/latest/doxygen/html/group__uart__interface.html)
- [Linux kernel documentation: Low Level Serial API](https://docs.kernel.org/driver-api/serial/driver.html)

## DBG-07 · 新板第一次上电没有任何输出，怎样推进 bring-up？

方向：MCU / Linux；难度：进阶；关键词：板级启动、bring-up、最小系统

### 面试官可能这样问

一块新板上电后串口没有字，你会从哪里开始？怎样区分根本没执行、时钟错误、引脚复用错和日志配置错？

### 考查意图

用从底层到上层的可观测检查建立启动里程碑，避免同时启用整个软件栈后失去定位边界。

### 30—60秒口述参考

我按供电复位、启动选择、调试连接、复位入口、时钟、最小 GPIO、串口轮询、内存和驱动逐步确认，每步只加入一个依赖，并记录能独立观察的里程碑。串口无输出不等于 CPU 没运行，先用调试器和简单 GPIO 区分。MCU 核对向量与链接地址，Linux 板按 ROM、早期引导、Bootloader、内核和根文件系统分段。板卡描述、引脚和时钟必须与实际硬件版本一致。

### 从不依赖软件日志的证据开始

先核对板卡版本、供电范围与关键电源轨、复位信号、启动配置和调试连线，测量应由具备条件的人员按板级要求进行，不能照抄其他板电压。调试器可连接时，观察复位后 PC、SP 和是否反复复位；不能连接时先查供电、复位保持、调试引脚复用及芯片安全状态。避免一开始就擦除全部存储或改不可逆保护位。

### 最小程序逐个验证依赖

在所用芯片支持的安全时钟条件下，从内部可用存储器执行最小循环，验证 GPIO 后再增加串口轮询，最后才加入中断、DMA、RTOS 和外部 RAM。若 GPIO 正常而串口不通，重点转向引脚复用、外设时钟、分频、路由和输出配置。外部 RAM 初始化代码本身不能依赖尚未初始化的外部栈或全局数据，链接布局要配合启动顺序。

### 软件描述必须落到物理资源

使用 Zephyr 时，板定义、Devicetree、pinctrl、Kconfig 和所选 SoC 共同影响实例与驱动启用；编译通过不证明引脚焊到了预期接口。Linux 板还应标明最后一个成功引导阶段，用对应阶段的早期日志或标记定位，而不是在用户态服务没启动时直接改串口驱动。每个里程碑保留镜像、配置和测量记录，方便硬件返修或下版板对照。

### 连续追问

**1. 为什么下载运行正常，掉电再上电失败？**

调试器可能预先初始化时钟或 RAM、设置入口、保留存储内容或改变复位方式。必须单独验证冷启动，比较启动映射、运行库初始化和电源时序，不能把调试下载路径当真实启动路径。

**2. 能直接借用相近板的配置吗？**

可以作为起点，但要逐项审查晶振、Flash/RAM 容量、引脚、外设实例、启动布局和电源控制。型号相近仍可能在封装引脚或总线可达性上不同，不能因为 LED 亮了就跳过核对。

**3. 怎样给硬件同事提供有效线索？**

提供具体板号、测点、期望与实测值、复位和时钟波形、最小可复现固件及最后成功里程碑。把“串口没字”变成“GPIO 已执行、UART TX 引脚无翻转或波特率偏差”的事实，便于分工验证。

### 容易答错的地方

- 串口没日志就直接判 CPU 未启动：可能仅输出路径尚未配置或被日志后端延迟。
- 同时改时钟、链接脚本与多组引脚后才测试：成功或失败都难以归因。

### 动手验证

为一块假想 MCU 板列八个按依赖排序的里程碑，每步写独立观测方法和失败后的下一检查；补一项脱离调试器的冷启动验收。

## DBG-08 · 怎样把一次修复变成长期有效的自动回归与故障注入测试？

方向：通用 / MCU / Linux；难度：深入；关键词：回归测试、故障注入、自动化

### 面试官可能这样问

修好了超时后资源泄漏，除了跑一晚不崩，你会补什么测试？自动报告写“构建通过”是否等于在板上验证通过？

### 考查意图

把根因转化为可观察不变量，区分构建、执行与验证范围，并让异常路径稳定可重现。

### 30—60秒口述参考

我先写能让旧版本失败、修复后通过的最小回归，再覆盖正常、边界、取消和失败清理；故障注入按指定次数让申请、I/O 或通知失败，验证资源和状态不变量。纯逻辑放主机快速测试，时序和外设契约上模拟器或目标板。报告明确构建成功、实际执行、跳过和失败原因，并保存版本、配置、随机种子及原始日志。持续通过只能覆盖已测范围，不能替代硬件与现场边界说明。

### 先定义失败判据而不是先写脚本

泄漏修复的判据可以是每轮断开后活跃对象回到基线、没有迟到回调访问已销毁对象，并在限定时间内完成取消。若测试只断言程序仍活着，它可能漏掉增长或状态错误。测试替身要保留真实接口的所有权和错误语义，例如发送失败是否仍持有缓冲区；否则测试覆盖了一个实际系统不存在的理想接口。

### 让难走分支按计划出现

为第 N 次分配失败、部分读取、重复通知、延迟完成和超时设计确定触发点，逐一检查清理和重试上限。支持环境可用内核已有故障注入设施，但必须在隔离测试机或测试板按目标范围启用，避免把随机破坏当测试方法。每次失败都记录注入位置、时序与输入；随机压力保存种子，同时保留真正触发交错的事件记录，因为种子未必能控制操作系统调度。

### 分层执行并如实汇总

主机单元测试快速验证解析和状态机，模拟器检查更多运行环境，目标板验证中断、DMA、缓存和真实外设时序。Zephyr 的 Twister 可组织多个平台与配置，但某实例可能只是构建、被过滤或跳过，必须查看实际运行状态，不能把总命令返回成功写成全部板测通过。版本二分脚本也应区分好、坏与无法测试，基础设施故障不应伪装成产品通过。

### 连续追问

**1. 故障注入是不是越随机越好？**

随机适合探索未知组合，但确定性注入更适合证明某条失败清理路径。两者结合：先按每个已知失败点系统覆盖，再做受界限约束的随机组合，并记录足够信息用于复现。

**2. 回归测试偶发失败能先自动重试变绿吗？**

可重试用于收集稳定性信息，但不能抹掉首轮失败。记录重试率、环境和原始证据，区分产品竞争与基础设施波动；最终报告应保留不稳定状态，避免长期掩盖真实缺陷。

**3. 修复提交通过后还需哪些验收？**

确认测试确实能使旧实现失败、没有依赖实现细节自证正确；再用发布配置和代表性负载测试，检查性能、内存和接口行为无回退。对未能在模拟器覆盖的硬件条件，单独写目标板验证结果与限制。

### 容易答错的地方

- 只统计测试条数而不看是否实际运行、是否有断言和是否覆盖旧缺陷。
- 把无法构建、设备断线或超时一律当产品通过：会污染回归与版本二分判断。

### 动手验证

为“异步请求取消后资源未回收”写四条不变量与六个确定注入点，给主机、模拟器和目标板分配验证责任；报告中分别列执行通过、仅构建、跳过与失败。
