## CODE-01 · 手写环形缓冲区：判空判满和并发边界

方向：通用；难度：进阶；关键词：ring、C代码、边界测试

### 面试官可能这样问

请实现一个固定容量的字节FIFO。如果生产者在中断里、消费者在任务里，你刚写的代码还能直接用吗？

### 考查意图

看你能否先定义容量和失败语义，再维护索引不变量；追问并发时，能否主动承认单线程代码不等于无锁队列。

### 30—60秒口述参考

采用读索引tail和写索引head，二者相等表示空，写索引下一位等于tail表示满，因此数组16字节实际最多存15字节。写入成功才发布head，取出成功才推进tail，满时返回失败且不覆盖旧数据。这份示例限定单线程或外部保护；若用于ISR与任务，还要证明索引原子访问、发布次序、编译器和硬件内存顺序，并确认目标上的原子操作适合ISR。

### 先定义接口契约

面试前先问满时丢新数据、覆盖旧数据还是阻塞。这里选择丢新数据并返回false，由上层累计溢出次数；这样接收链路能报告真实丢包，而不是悄悄破坏帧。初始化必须清零，head和tail始终小于RB_CAP。

留空一格是编码状态的一种选择，不是环形缓冲区只能这样做。使用独立count可以填满全部数组，但count变成双方共同修改的数据，并发证明更复杂。也可以使用单调序号，但必须证明回绕和距离比较的范围。

### 一份有明确边界的实现

代码用取模使索引回到数组开头，容量固定16。push先判断下一位置，满时不改变任何索引或数据；pop在空时不修改输出参数。为便于独立练习，头文件和测试main放在“03_代码练习/01_ring.c”。

这段C代码并未加入volatile或原子限定，不能因为head只由生产者写、tail只由消费者写就直接宣称线程安全。Linux用户态的C线程并发需符合语言内存模型；MCU中断属于具体编译器和平台环境，还要核对ISR约束。

```c
#define RB_CAP 16u
typedef struct { uint8_t data[RB_CAP]; size_t head, tail; } Ring;
/* Single-thread use, or protect each operation externally. */
bool rb_push(Ring *r, uint8_t value) {
    if (!r) return false;
    size_t next = (r->head + 1u) % RB_CAP;
    if (next == r->tail) return false;
    r->data[r->head] = value;
    r->head = next;
    return true;
}
bool rb_pop(Ring *r, uint8_t *out) {
    if (!r || !out || r->head == r->tail) return false;
    *out = r->data[r->tail];
    r->tail = (r->tail + 1u) % RB_CAP;
    return true;
}
```

### 从正确性到吞吐验证

测试应至少覆盖初始空、正好写15次、第16次拒绝、FIFO顺序、读空时输出不变、读写交错跨越多次数组边界。不要只用一个hello字符串测“能收到”。可维护一个简单参考队列，与随机操作逐步对照。

工程容量要按最坏服务间隔估算：输入速率乘以消费者最长不能运行的时间，再加突发余量；若长期输入速率高于处理速率，增大缓冲只能延后失败。上层必须定义溢出后的重新同步策略。

### 连续追问

**1. 加volatile就够了吗？**

不够。volatile既不构成C线程同步，也不保证复合操作原子或普通内存的发布顺序。需要根据平台使用正确的临界区、原子release/acquire或RTOS队列；ISR可用性还必须单独验证。

**2. 两生产者还能沿用这个算法吗？**

不能直接沿用。两个生产者可能同时读到同一个head并覆盖同一槽。应串行化生产端、用多生产者队列或重新设计序号协议，不能只把head类型改成atomic就认为算法正确。

**3. DMA可以直接写这个数组吗？**

必须重新设计DMA写入位置、半满/满事件、跨圈检测与缓存一致性。CPU发布的head和DMA实际写完成不是同一件事，还要防止CPU读取DMA尚未完成的数据。

### 容易答错的地方

- 把16字节数组宣传为16字节有效容量，会让满判断与文档不一致。
- 覆盖旧数据却仍返回成功，可能把完整帧悄悄变成无法检测的混合内容。
- 对普通C变量进行并发读写再依靠“测试没出错”，无法证明线程安全。

### 动手验证

先不看代码实现同样接口，再运行对应C文件的测试；随后写出用RTOS队列替代时容量、拷贝成本和ISR接口的差异。

- [WG14 N1570：C11 委员会草案（类型、整数运算、对象与库函数）](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

## CODE-02 · 写一个能处理半包、连包和坏包的字节流解析器

方向：通用；难度：进阶；关键词：parser、C代码、边界测试

### 面试官可能这样问

串口每次给你的字节数不固定，可能一次半帧，也可能两帧一起到。请设计解析器，而不是假设一次接收就是一帧。

### 考查意图

看是否把传输分片与业务帧边界分开，是否在写缓冲之前检查长度，以及错误输入能否恢复到一个明确状态。

### 30—60秒口述参考

用持久状态机逐字节处理，状态依次为等帧头、收长度、收数据、校验。接收函数调用的边界不影响解析状态，拿到完整合法帧才提交输出。示例用A5帧头、0至64字节负载和异或校验，非法长度与校验失败回到等帧头；这只是教学协议，生产设计应补超时、可靠的帧界定和更强完整性校验。

### 把分片问题变成状态问题

解析器对象保存state、len、used和校验累积值。一次收到几个字节，只是调用feed几次；一次只收到帧头也要保留READ_LEN等待后续。完整帧之前不让业务读取临时缓冲，输出对象仅在返回1时更新。

本协议允许负载包含A5，因为进入READ_DATA后按长度计数，不再把A5当新帧。长度字段最大64，必须在设置收数状态前拒绝更大的值。0长度直接等校验字节，避免把空帧误判成永远收不完。

### 原地解析并在成功时提交

示例返回0表示继续收，1表示得到帧，-1表示输入或状态错误。Parser用全零初始化；Frame由调用方持有。完整源码练习包含空帧、最大长度、多个连续帧和输出不被坏包覆盖等断言。

这里只演示内存安全和分片处理，异或校验可被有意构造碰撞，也可能漏掉多位错误。它不是CRC，更不是认证。示例在错误后丢弃当前字节再找下一个帧头，并不承诺对任意插入/删除字节都能立刻恢复。

```c
enum { WAIT_HEAD, READ_LEN, READ_DATA, READ_SUM };
typedef struct { unsigned state; uint8_t len, used, sum, data[64]; } Parser;
typedef struct { uint8_t len, data[64]; } Frame;
/* A5, length(0..64), payload, XOR(length and payload). */
int parser_feed(Parser *p, uint8_t byte, Frame *out) {
    if (!p || !out) return -1;
    switch (p->state) {
    case WAIT_HEAD:
        if (byte == 0xA5u) p->state = READ_LEN;
        return 0;
    case READ_LEN:
        if (byte > 64u) { p->state = WAIT_HEAD; return -1; }
        p->len = byte; p->used = 0; p->sum = byte;
        p->state = byte ? READ_DATA : READ_SUM;
        return 0;
    case READ_DATA:
        p->data[p->used++] = byte; p->sum ^= byte;
        if (p->used == p->len) p->state = READ_SUM;
        return 0;
    case READ_SUM:
        p->state = WAIT_HEAD;
        if (byte != p->sum) return -1;
        out->len = p->len;
        memcpy(out->data, p->data, p->len);
        return 1;
    default:
        p->state = WAIT_HEAD; return -1;
    }
}
```

### 生产系统还缺哪些条件

还需要帧接收超时，否则合法长度后永久缺少尾字节会占住解析状态；超时用单调时钟并明确重置时机。若噪声中的伪帧头导致错误长度，应用层要选用转义、固定头校验、可靠长度字段或COBS等完整设计。

验证时把同一个字节流在每个可能位置拆分，解析结果应一致；再加入坏长度、截断、错误校验和恢复后的合法帧。长期随机输入可配合越界检测器运行，检查状态与used永远处于允许范围。

### 连续追问

**1. 为什么不能在UART空闲中断直接认定一帧？**

空闲事件描述线路时隙，不一定等于业务帧边界。对明确以时间间隔分帧的协议可以按规范使用；对长度帧协议，空闲只适合搬运数据，最终边界仍应由解析器判断。

**2. 出现校验错误后，从哪里继续？**

必须由协议决定。简单回到等帧头易实现，但可能错过嵌套在坏包中的真实帧头；更复杂的恢复需要明确帧头唯一性、头部校验或转义规则，不能无依据承诺丢一个字节就一定恢复。

**3. 解析和业务执行要放在ISR吗？**

通常ISR只搬运或发布已完成数据，解析和业务放在线程/任务。若解析在ISR，必须界定每次最大处理量，不能分配堆或阻塞；共享状态和输出队列也要保证上下文安全。

### 容易答错的地方

- 用memcpy复制长度字段指定的任意字节数，然后才判断长度，会先发生越界。
- 把TCP一次recv或UART一次DMA完成当作一帧，是把传输交付边界误当协议边界。
- 讲到校验失败只说“重发”，却没有错误计数、超时和恢复状态。

### 动手验证

画出四个状态的所有转换，给每条错误边写一个测试；扩展一个明确的超时重置接口，再说明定时器回绕如何处理。

- [Clang AddressSanitizer：内存访问错误检测](https://clang.llvm.org/docs/AddressSanitizer.html)

## CODE-03 · 定时计数器回绕后，超时判断怎么写

方向：通用；难度：进阶；关键词：tick、C代码、边界测试

### 面试官可能这样问

系统tick是32位毫秒，跑很久后归零。为什么now >= start + delay会出问题？请写出替代逻辑并说明它也有什么限制。

### 考查意图

考查无符号模运算、时钟语义和适用时间范围，避免只背一个公式却无法解释停机、跨多圈和时钟回拨。

### 30—60秒口述参考

在单调32位计数器、真实经过时间小于一整圈的前提下，用无符号差值(uint32_t)(now-start)比较delay，跨一次零点仍得到正确经过量。示例把delay限制在INT32_MAX以内以简化调用契约，但仍要求及时检查，不能把跨多圈丢失的信息恢复出来。Linux用户态计算时长优先选择符合休眠语义的单调时钟，而不是日历时间。

### 先算出一个反例

假设start为0xFFFFFFF0，delay为32；start+delay按32位回到16。只看now>=16，在真正超时前、now还很大时就可能误判。若now为0x00000010，无符号now-start得到32，刚好到期。

这种方法依赖固定模数：32位无符号减法转换后的结果等于真实差值模2^32。只有知道真实经过量小于一整圈，才可以把模值解释为真实经过时间。把类型随意改成有符号int会引入另一组规则。

### 实现与约束必须一起交付

本例返回false拒绝超过INT32_MAX的delay；正式接口可改成错误码，让非法参数与“尚未到期”区分开。start必须取自同一计数器过去的采样；不能把其他时钟、网络时间戳或未来开始时间混进来。

32位1毫秒tick约49.7天绕一圈。示例不是“只能运行49天”，而是单次区间必须按契约观测；系统可以运行多年，只要每个定时任务及时采样、更新自己的起点，且计数读取本身一致。

```c
/* Preconditions: monotonic 32-bit ticks; start is in the past;
   elapsed real ticks since start < 2^32; delay <= INT32_MAX. */
bool expired32(uint32_t now, uint32_t start, uint32_t delay) {
    if (delay > INT32_MAX) return false;
    return (uint32_t)(now - start) >= delay;
}
```

### 区分周期策略和休眠语义

周期任务到期后写start=now会随执行延迟漂移；写start+=period保持原相位，但落后多个周期时要决定追赶、合并还是跳过，不能用无限while把系统拖死。设计时把最大补偿次数写清楚。

Linux CLOCK_MONOTONIC不跟随日历时间突然跳变，但通常不计挂起时长；需要包含系统挂起可考虑CLOCK_BOOTTIME。MCU进入深睡后某些tick停止，要核对实际时钟来源和唤醒补偿，公式不能补救时钟语义选错。

### 连续追问

**1. 为什么常见deadline比较要求半圈范围？**

对两个循环时间戳判断谁在前谁在后，若跨度可能达到半圈就会出现顺序歧义。elapsed差值和有符号deadline比较不是同一个证明；要分别说明范围和转换规则，不能只抄强转int32_t。

**2. 关闭中断很久，tick会不会少计？**

可能。若tick来自每周期一次中断，而硬件只记一个挂起位，多次溢出未必逐次补发。要看定时器、内核移植和补偿机制；读取硬件自由运行计数器与累计中断次数有不同误差。

**3. 64位时间戳在32位MCU能直接读吗？**

不一定是不可分割读取。两个32位部分之间可能发生更新；可用目标允许的原子读取、短临界区或带重试的一致快照。volatile不会自动把64位读取变成原子操作。

### 容易答错的地方

- 把“无符号减法支持回绕”夸大成任意停机时长都不会失效。
- 用系统日历时间计算协议超时，调时后可能突然提前或延后。
- 把周期任务每次start=now的漂移误认为计数器精度问题。

### 动手验证

手算start=0xFFFFFFF0时now为0xFFFFFFF5、0、16的差值。再说明系统睡眠一天后你的定时器应算睡眠时长还是暂停。

## CODE-04 · 把十进制字符串转成uint32_t，怎样避免溢出

方向：通用；难度：进阶；关键词：parse、C代码、边界测试

### 面试官可能这样问

不用atoi，写一个严格的无符号十进制解析函数。输入不是NUL结尾字符串，而是指针和长度；失败时不要破坏调用方已有值。

### 考查意图

考查长度边界、字符范围、溢出前置判断与失败原子性，区分“看起来能转换”与可用于协议字段的接口。

### 30—60秒口述参考

先定义只接受一个或多个ASCII数字，不接受正负号和空白。逐字符累积value，在计算value*10+digit之前检查value <= (UINT32_MAX-digit)/10。直到所有字符通过才写回out，因此错误字符、超范围或空输入都不会破坏旧输出。指针加长度仍依赖调用方提供真实可读范围，函数无法凭空验证内存对象大小。

### 把模糊输入规则变成接口契约

配置字符串与协议字段可能需要不同规则：前导空白是否允许、加号是否允许、空字符串等于0还是错误、前导零是否接受。示例接受前导零但拒绝其他非数字，避免把12xyz解释成12而使上层误以为整个字段有效。

长度参数说明本函数不寻找NUL。若输入里有嵌入的0字节，它也不是ASCII数字，因此失败；这样调用方不会因为日志显示被NUL截断而误判实际解析内容。字符串编码按ASCII数字定义，中文全角数字不会被隐式接受。

### 在算术发生之前判断上限

如果先执行value=value*10+digit再与UINT32_MAX比较，溢出的数学信息已经丢失。示例从不等式推出前置条件，并在所有字符通过后一次提交。每次digit最大9，所以UINT32_MAX-digit本身不下溢。

这里使用unsigned char读取字符，再与字符常量比较，不依赖普通char是否有符号。整体时间复杂度为O(len)、额外空间O(1)。实时链路仍应在上层限制字段长度，不能让攻击性巨长输入占用无界时间。

```c
/* Accept only 1+ ASCII decimal digits. On failure, *out is unchanged. */
bool parse_u32(const char *s, size_t len, uint32_t *out) {
    if (!s || !out || !len) return false;
    uint32_t value = 0;
    for (size_t i = 0; i < len; ++i) {
        unsigned char c = (unsigned char)s[i];
        if (c < '0' || c > '9') return false;
        uint32_t digit = (uint32_t)(c - '0');
        if (value > (UINT32_MAX - digit) / 10u) return false;
        value = value * 10u + digit;
    }
    *out = value;
    return true;
}
```

### 用边界和性质验证

必须测0、4294967295、4294967296、空输入、负号、空白、末尾字母、嵌入NUL和前导零。每个失败案例把out预置哨兵值，然后确认哨兵未变，才能证明失败没有半写回。

可再生成很多uint32_t值，用可信的格式化函数转换成十进制文本后喂给解析器，检查往返一致。测试只覆盖整数解析这个局部，不能替代整条协议对字段长度、版本和权限的校验。

### 连续追问

**1. atoi为什么不合适？**

它的错误区分能力有限，也不提供这里所需的严格范围与结尾消费契约。使用strtoul等标准接口时仍需检查errno、endptr、类型上限与允许的符号空白，不能调用完就算校验成功。

**2. 前导零一百万个最后跟1，数值没超限能接受吗？**

算术上可以，但时间开销不应无界。协议应该限制文本字段最大字节数；是否允许很多前导零是格式策略，不能只用数值范围替代资源限制。

**3. 如何推广到有符号32位？**

先解析符号，再用足够宽或无符号中间量检查正负不同上限，注意INT32_MIN的绝对值不能用int32_t表示。不要简单先调用abs或对INT32_MIN取负。

### 容易答错的地方

- 先溢出再检测，已经失去正确的数学结果。
- 遇到第一个非数字就返回已累积值，悄悄接受了无效字段。
- 把输出指针非空误当作输出指针一定有效。

实现一个有符号32位版本，明确INT32_MIN、INT32_MAX、正负零和只有符号无数字的结果，并给出失败不改输出的测试。

## CODE-05 · 解析网络字节序：为什么不能直接强转指针

方向：通用；难度：进阶；关键词：endian、C代码、边界测试

### 面试官可能这样问

缓冲区偏移3（第4个字节）开始有一个32位大端字段。你会写*(uint32_t *)(buf+3)吗？请给出不依赖地址对齐和CPU字节序的实现。

### 考查意图

考查字节序、对齐、整数提升和边界校验，能否区分常见平台巧合与可移植C语义。

### 30—60秒口述参考

按字节读取，并在左移之前转成uint32_t，明确拼出大端数值。先检查offset<=size，再检查size-offset>=4，避免offset+4本身溢出。直接强转既可能未对齐，又受本机字节序与对象访问规则影响。memcpy可以解决某些对齐和别名问题，但它不会自动把网络大端变成本机数值。

### 先保证范围，再形成地址

C指针加法不是任意整数地址运算，必须落在合法对象范围或规定的末尾位置。示例先验证偏移和剩余长度，再生成data+offset。调用方仍须保证size真实对应缓冲区可访问范围，不能把虚报size交给函数。

常见检查offset+4>size在offset接近SIZE_MAX时可能回绕。使用offset>size || size-offset<4分两段检查，后面的减法只有在前项为假时求值；短路求值在这里是正确性证明的一部分。

### 明确的字节装配与拆分

每个字节先转换成uint32_t再移位，使最高位为1的字节左移24位仍在无符号运算语义内。若先让uint8_t提升到有符号int再左移，特定值可能产生未定义行为。写回时用右移和窄化只保留所需字节。

代码适用于提供uint8_t与uint32_t的实现。本练习字段明确是4个8位字节，不应该在没有这类精确宽度类型的平台上悄悄用unsigned long替代，因为long宽度随ABI变化。

```c
bool read_be32(const uint8_t *data, size_t size, size_t offset,
               uint32_t *out) {
    if (!data || !out || offset > size || size - offset < 4u)
        return false;
    const uint8_t *p = data + offset;
    *out = ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16)
         | ((uint32_t)p[2] << 8) | (uint32_t)p[3];
    return true;
}
bool write_be32(uint8_t *data, size_t size, size_t offset, uint32_t v) {
    if (!data || offset > size || size - offset < 4u) return false;
    data[offset] = (uint8_t)(v >> 24);
    data[offset + 1] = (uint8_t)(v >> 16);
    data[offset + 2] = (uint8_t)(v >> 8);
    data[offset + 3] = (uint8_t)v;
    return true;
}
```

### 协议布局不要借用结构体布局

即使给结构体加packed，也仍要处理端序、访问对齐及编译器扩展。业务结构体可以保留自然对齐；在线上字节流边界集中做序列化和反序列化，让协议版本与CPU内存布局分开。

测试0、1、0x80000000和0xFFFFFFFF，验证写后读相等，以及期望字节序列。用非对齐偏移3、缓冲区不足4字节、offset等于size和SIZE_MAX测试拒绝路径，确认写失败不会改变缓冲区。

### 连续追问

**1. memcpy(&value,buf,4)是不是就好了？**

它可避免直接未对齐类型访问等问题，但读出的value仍按本机字节序解释。还需端序转换，且先验证长度；不要把内存安全与协议编码正确混为一件事。

**2. 为什么位域结构不适合直接发到总线？**

位域的分配顺序、跨存储单元方式和填充与实现有关，不能当作跨编译器协议。应明确每一位的编号、取值范围和序列化方式，位运算掩码也要避免过宽移位。

**3. 大小端检测应该运行时做吗？**

这种逐字节装配实现本身不需要检测。性能敏感时可以使用经过验证的库函数或编译器内建，让优化器生成适合目标的代码；先保证语义，再测实际瓶颈。

### 容易答错的地方

- 先移位再强转，可能已经在有符号int范围发生未定义行为。
- packed结构体消除所有协议兼容问题，是错误的概括。
- 用offset+length检查却没考虑加法溢出。

### 动手验证

增加16位字段读取，并设计一个版本号+长度+数值的线格式；写出固定字节测试向量，确认在不同端序机器上的数值解释一致。

## CODE-06 · 不用阻塞延时，写一个按键消抖状态机

方向：通用；难度：进阶；关键词：debounce、C代码、边界测试

### 面试官可能这样问

按键抖动持续几毫秒，但你的系统还要处理通信。不能在检测到按下后delay(20)，你怎样实现消抖并避免一次长按触发很多次？

### 考查意图

看能否把事件、稳定状态、候选状态和经过时间分开，处理上电初值、释放边沿、采样间隔与时间回绕。

### 30—60秒口述参考

每次采样保存候选电平，候选变化时重记起点；候选持续20毫秒且不同于已确认状态，才提交新状态并返回一次边沿事件。状态提交后持续按住不再重复触发；释放也独立消抖。示例使用高电平有效，并要求初始化使用实际电平。时间单位为毫秒，按键硬件若为低有效，应在输入层先归一化。

### 先区分稳定电平与一次事件

stable是已确认的逻辑电平，candidate是最近观察到且等待确认的电平，since是这个候选首次被观察到的时间。若原始电平在候选稳定20毫秒前反转，就重启确认窗口。事件只发生在stable真正变化时。

上电时按键已按下是否立即算一次按下，是产品需求。示例初始化为实际电平，因此不会凭空发一个边沿；若要上电按住进入维护模式，应设计单独的启动判定，不能依赖未初始化结构体。

### 每次调用只做常数时间处理

此实现没有忙等或delay，适合周期扫描任务。调用频率决定时间分辨率：10毫秒扫描无法承诺1毫秒级事件时刻，20毫秒阈值也只是采样所见稳定时间，不是连续模拟信号的完整观测。

debounce_init和update要求有效对象指针；生产API可额外加入NULL防护。时间采用无符号差值，因此允许过零，但仍要求观测区间少于完整一圈。测试把起点放在0xFFFFFFF0附近验证跨界确认。

```c
typedef struct { bool stable, candidate; uint32_t since; } Debounce;
/* Initialize with the actual input level and initial tick. */
void debounce_init(Debounce *d, bool level, uint32_t now) {
    d->stable = d->candidate = level; d->since = now;
}
/* Active-high key; period between checks and total delay < one wrap.
   Return +1 press, -1 release, 0 no accepted edge. */
int debounce_update(Debounce *d, bool raw, uint32_t now) {
    if (raw != d->candidate) {
        d->candidate = raw; d->since = now;
    }
    if (d->candidate != d->stable &&
        (uint32_t)(now - d->since) >= 20u) {
        d->stable = d->candidate;
        return d->stable ? 1 : -1;
    }
    return 0;
}
```

### 扩展长按和连发时保持分层

消抖层输出逻辑边沿，上层再用已确认按下起点识别长按、双击与连发。把所有功能塞进一次raw==1判断会导致边沿重复或释放丢失。双击要定义第一击释放后等待窗口，以及单击何时对外确认。

若靠GPIO中断唤醒，ISR里可以记录事件并开启扫描或定时器，不应在中断里忙等20毫秒。低功耗系统还要评估抖动导致重复唤醒的能耗，并按硬件能力考虑输入滤波或RC网络。

### 连续追问

**1. 20毫秒是所有按键的标准吗？**

不是，是示例阈值。要根据开关、硬件滤波、使用体验和实测波形选取。面试回答可说先采集抖动范围，再选阈值并验证高低温、老化及极端操作。

**2. 一次调度卡住100毫秒怎么办？**

采样无法知道这100毫秒内真实发生了什么。恢复后算法只能处理看到的电平，不能保证识别期间所有短按；若需求必须捕获，应评估硬件锁存、输入捕获或中断记录。

**3. 如何避免一次长按既触发长按又触发单击？**

在上层手势状态中记录long_fired，长按确认后释放不再发单击；单击和双击也要有明确优先规则。消抖负责稳定边沿，不替代手势语义。

### 容易答错的地方

- 在ISR里delay消抖会延长中断占用并阻塞更低优先级处理。
- 每次扫描raw为按下就发事件，长按会被当成很多次点击。
- 只消抖按下、不消抖释放，会使双击和长按逻辑出现伪边沿。

### 动手验证

把高低电平与时间写成一张表，覆盖抖动、短于阈值的脉冲、稳定长按、释放抖动、上电按住和tick回绕，逐项写期望事件。

- [WG14 N1570：C11 委员会草案（类型、整数运算、对象与库函数）](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)
- [Linux man-pages：clock_gettime 与单调时钟](https://man7.org/linux/man-pages/man3/clock_gettime.3.html)

## CODE-07 · 固定块内存池：满池、重复释放与陈旧句柄

方向：通用；难度：深入；关键词：pool、C代码、边界测试

### 面试官可能这样问

系统禁止运行期malloc。请设计8个固定块的池，并解释已经释放的旧句柄为什么不应该释放掉后来重新分配的块。

### 考查意图

不仅考查分配回收，更看所有权、ABA式复用、对齐、容量策略、版本回绕与线程安全边界。

### 30—60秒口述参考

用固定数组和占用标志管理有限个字节块，句柄包含槽号和世代号。每次分配增加该槽世代，释放先核对范围、占用和世代，旧句柄就不会错误释放新对象。示例在世代耗尽时退役该槽而不是回绕复用，限定单线程并只提供字节存储；它不是支持任意类型对齐和并发的通用malloc。

### 先给资源上限和句柄生命周期

8个32字节块的有效数据容量是256字节，此外还要计入标志、世代和对齐填充，不能把池对象总sizeof也说成256。满时分配失败且out保持原值；调用方应决定拒绝请求、等待或使用备用资源。

仅检查used无法识别旧句柄：A释放槽0，B又占用槽0，A若重复释放就会误释放B。世代号把同一池当前生命周期内的分配身份区分开。句柄只属于原池实例，不能跨池使用；重新初始化前必须确保所有旧句柄停止使用，否则清零后的世代可能再次相同。它不是加密令牌，也不能阻止能修改内存的程序伪造句柄。

### 实现身份检查，并拒绝世代回绕

槽世代初始0，成功分配递增为非零。到UINT32_MAX后该槽释放仍可执行，但不再分配；这样不会在回绕后让极老句柄再次有效。正式系统需评估计数宽度和最大生命周期，不能假设32位永远不耗尽。

本例故意不返回可长期持有的原始指针，因为释放后继续读写原始指针无法靠句柄检查阻止。若增加读写函数，每次先验证句柄，再验证offset和length；多线程环境须把验证与访问放在同一保护范围。

```c
#define POOL_N 8u
#define BLOCK_BYTES 32u
typedef struct { uint8_t slot; uint32_t generation; } Handle;
typedef struct {
    bool used[POOL_N]; uint32_t generation[POOL_N];
    uint8_t bytes[POOL_N][BLOCK_BYTES];
} Pool;
/* Byte-storage handles only; not a general malloc replacement. */
bool pool_valid(const Pool *p, Handle h) {
    return p && h.slot < POOL_N && p->used[h.slot] &&
           p->generation[h.slot] == h.generation;
}
bool pool_alloc(Pool *p, Handle *out) {
    if (!p || !out) return false;
    for (unsigned i = 0; i < POOL_N; ++i) {
        if (!p->used[i] && p->generation[i] != UINT32_MAX) {
            ++p->generation[i]; p->used[i] = true;
            memset(p->bytes[i], 0, BLOCK_BYTES);
            out->slot = (uint8_t)i; out->generation = p->generation[i];
            return true;
        }
    }
    return false;
}
bool pool_free(Pool *p, Handle h) {
    if (!pool_valid(p, h)) return false;
    p->used[h.slot] = false;
    return true;
}
```

### 不要漏掉对齐与并发成本

存储定义为uint8_t数组，适合复制协议字节。把它直接强转为任意结构体可能不满足对齐和对象访问规则；想支持通用对象，应设计合适的对齐、初始化与析构策略，C++对象还涉及生命周期。

小固定池线性扫描8槽是可预测上界的选择；更大池可以用空闲链表或位图，但同步和损坏检测会更复杂。测试满池、回收后复用、非法槽、重复释放、旧世代释放失败和世代最大值退役。

### 连续追问

**1. 世代号让池线程安全吗？**

不。两个线程仍可同时选到同一空槽，或在校验后被另一线程释放。世代解决身份复用，不解决互斥；需要锁、临界区或经证明的并发算法。

**2. 能在ISR分配吗？**

只有实现的时间上界、同步方式和调用契约都适合ISR才可以。示例是单线程代码，不能直接共享到任务与ISR；也不能在ISR等可能被任务持有的阻塞互斥锁。

**3. 释放时把指针设NULL能彻底防止UAF吗？**

只能清掉当前这一个变量，其他别名仍可能存在。所有权纪律、句柄校验、生命周期设计和检测工具需要一起使用；把一个局部变量置NULL不等于撤销所有引用。

### 容易答错的地方

- 把used检查当作能识别所有重复释放，会漏掉槽已经再次分配的情形。
- 忽略对齐，把字节数组地址直接当任何结构体地址使用。
- 把世代号当同步原语，忽略检查与使用之间的竞态。

### 动手验证

给本池补一个安全写入接口，要求检查offset、length、句柄并在失败时不改变数据；画出A释放、B复用、A旧句柄再释放的时序。

- [WG14 N1570：C11 委员会草案（类型、整数运算、对象与库函数）](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)
- [Clang AddressSanitizer：内存访问错误检测](https://clang.llvm.org/docs/AddressSanitizer.html)

## CODE-08 · 写滑动平均：累加器位宽、启动阶段与延迟

方向：通用；难度：进阶；关键词：average、C代码、边界测试

### 面试官可能这样问

ADC输出int16_t，你要计算最近8个采样的滑动平均。不想每次循环加8次，怎样做到每次O(1)？负数和刚启动时怎么处理？

### 考查意图

考查从数据范围推导算术位宽、环形窗口、启动策略，以及滤波精度与响应时间的实际取舍。

### 30—60秒口述参考

维护8点环形数组和int32_t累加和，窗口满后先减掉被替换的旧值，再加新值；未满时只增加有效样本数。平均值用sum除以当前count，避免启动阶段默认补零拉低结果。8个int16_t的和在int32_t范围内，但以后扩大窗口或引入增益需重新推导。整数除法按C99及以后规则向零截断，不等于四舍五入。

### 先证明数值范围

int16_t最小-32768、最大32767，8点和范围为-262144到262136，可由int32_t表示。更新顺序先减旧再加新，中间量也保持在相应7点或8点范围内。若先加新再减旧，会暂时出现9点总和，扩展设计时同样要检查。

返回平均值仍落在输入值范围内，因此可转换回int16_t。这个结论依赖count至少为1且sum确实对应有效样本；不能用未经初始化的count或错误的环形索引去支撑数学证明。

### 常数时间更新的实现

结构体全零初始化。窗口未满时先增count，满后才减旧；pos每次推进一格。平均采用当前已有样本数，因此第一个输入100直接输出100，而不是12。完整练习中同时用朴素重算窗口作为独立参考。

调用者要提供有效Average指针，示例没有线程同步。若ISR写入、任务读取过滤结果，应设计一个明确的结果发布接口；不要让任务随意读取正在更新的sum、count和values组合。

```c
#define AVG_N 8u
typedef struct {
    int16_t values[AVG_N]; unsigned pos, count; int32_t sum;
} Average;
/* Single-thread model, initialized to all-zero. */
int16_t average_push(Average *a, int16_t sample) {
    if (a->count == AVG_N) a->sum -= a->values[a->pos];
    else ++a->count;
    a->values[a->pos] = sample;
    a->sum += sample;
    a->pos = (a->pos + 1u) % AVG_N;
    return (int16_t)(a->sum / (int32_t)a->count);
}
```

### 滤波不等于没有代价

8点等权平均能降低某些不相关噪声，却会平滑阶跃并引入延迟。采样率变化会改变相同8点对应的时间窗，因此不能只说“加一个平均滤波就更稳定”，还要核对响应速度和需要保留的信号频率。

测试全最大值、全最小值、正负交替、缓慢斜坡、阶跃、跨多个索引周期，以及启动前7点。工程中还要确认ADC原始码是否本来无符号、偏置如何去除、饱和是否应先标记，而不是机械套用int16_t。

### 连续追问

**1. 为什么不用int16_t保存sum？**

两个大正数相加就可能超出int16_t可表示范围；即使表达式经整数提升计算，赋回过窄类型也会丢失所需值。累加器宽度应由最大样本幅度、窗口长度和增益共同推导。

**2. 负数除法结果怎样？**

C99及以后整数除法截去小数部分朝零靠近，例如-3/2为-1。若需要四舍五入，应针对正负分别设计且检查加偏置是否溢出；不能对所有sum一律加count/2。

**3. 增加窗口长度是不是总更好？**

不是。噪声抑制、内存开销、启动时间与响应延迟都变化；对尖峰干扰可能中值滤波更合适，对固定频率噪声则应基于采样率和频谱设计。先定义指标再选算法。

### 容易答错的地方

- 未满8点就固定除8，启动读数会被隐式补零拉偏，除非这正是明确的需求。
- 只关心最终和范围，忽略更新过程中的中间量可能更宽。
- 把均值结果叫“无损去噪”，忽略信号延迟与量化舍入。
