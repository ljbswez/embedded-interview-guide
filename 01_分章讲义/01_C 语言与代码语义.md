## C-01 · volatile 能保证中断与线程共享变量安全吗？

方向：通用 / MCU / Linux；难度：进阶；关键词：volatile、原子性、内存序

### 面试官可能这样问

主循环等一个标志位，中断把它置位，加 volatile 就够了吗？如果换成两个 Linux 线程，或者计数器自增，你会怎样处理？

### 考查意图

区分可观察访问、不可分割操作、跨执行上下文同步，并主动声明编译器和中断模型的前提。

### 30—60秒口述参考

volatile 主要约束编译器如何处理对该对象的访问，常用于寄存器和实现定义的中断共享场景；它不保证复合操作原子，也不是线程同步。线程共享状态应使用锁或 C11 原子并选择合适内存序。MCU 还需核对访问宽度、对齐、嵌套中断和原子实现能否在 ISR 使用。发布一块缓冲区时，我会连数据可见性和所有权一起设计。

### 把三个问题分开

可见访问解决“编译器是否保留需要的读写”，原子性解决“操作能否被打断成几部分”，同步解决“看到标志后能否看到先前的数据”。例如 volatile 计数器自增仍可展开为读、加、写，主循环与中断交错便会丢增量。即使某芯片对齐的字宽读写不可撕裂，也不能直接推出整个自增不可分割。

C11/C17 的线程数据竞争规则不因 volatile 而豁免。两个线程无同步地同时访问同一个普通对象、其中至少一个写，可能构成未定义行为；不能用一次测试没出错证明安全。硬件 ISR 与 ISO C 的线程、信号处理并不完全等价，必须结合工具链和 RTOS 约定回答。

### 一次性发布的例子

示例假设只有一个发布者，data 在发布前写一次，此后不再修改；接收者只有 acquire 读到 release 写入的 ready 后才使用 data。它展示的是发布关系，不是可反复覆盖的邮箱协议。若下一轮马上重写 data，还需要消费者确认、双缓冲或队列来避免并发读写。

```c
#include <stdatomic.h>
static int data;
static atomic_bool ready = ATOMIC_VAR_INIT(0);
void publish(void) {
    data = 42;
    atomic_store_explicit(&ready, 1, memory_order_release);
}
int try_read(int *out) {
    if (!atomic_load_explicit(&ready, memory_order_acquire)) return 0;
    *out = data;
    return 1;
}
```

### 在 MCU 上落地

若只在单核主循环和 ISR 之间共享少量状态，可用短临界区保存并恢复原中断屏蔽状态；不要退出时无条件开中断。若选择原子，要检查目标类型是否 lock-free、是否调用运行库及是否允许中断重入。中断优先级越高不代表可以调用所有 RTOS API；临界区能屏蔽哪些中断也需核实。

### 连续追问

**1. 为什么 relaxed 计数器有时足够？**

如果只需要精确累计独立事件，不用它发布其他对象，relaxed 原子读改写可以避免丢计数；但它不自动让另一个缓冲区的内容随计数一起可见。必须从这个计数承担的协议职责推导内存序。

**2. 给 ready 和 data 都加 volatile 呢？**

这仍没有建立 C 线程之间的 happens-before 关系，也没有互斥。GCC 明确指出 volatile 访问不能作为普通内存访问的通用屏障；应改同步协议，而不是逐个补限定符。

**3. 64 位原子在 32 位 MCU 上安全吗？**

不能只看类型名。编译器可能生成独占访问序列或外部库调用；后者可能含锁，在 ISR 中有死锁风险。检查 lock-free 查询、反汇编和所用运行库文档，再决定改为临界区或不同的数据表示。

### 容易答错的地方

- 把 volatile 等同于“永远从物理 RAM 取值”：它不绕过数据缓存，也不完成 DMA 一致性维护。
- 认为单核就没有竞争：中断与任务切换仍可穿插读改写。

### 动手验证

分别编译普通计数、volatile 计数和原子计数，查看优化后的反汇编；画出一次丢增量交错，再写出所选方案的执行上下文与保护范围。

## C-02 · const int *、int * const 和二级指针分别承诺什么？

方向：通用 / MCU / Linux；难度：基础；关键词：const、指针限定、接口契约

### 面试官可能这样问

我给你三个指针声明，你如何判断哪些赋值合法？API 返回 const 指针后，数据就一定永远不会变吗？

### 考查意图

判断限定符约束的是哪个对象，并区分类型上的只读视图、底层对象是否可改以及实际存储位置。

### 30—60秒口述参考

const int * 限制通过这个指针修改整数，指针本身能改；int * const 固定指针变量，目标整数通常仍能改。const 是访问契约，不等同于 Flash 放置或线程安全。若对象本来定义为 const，去限定后写它是未定义行为；若底层本来可写，另一合法别名仍可能改变值。二级指针不能套用一级指针的简单添加 const 规则。

### 从标识符向外读声明

先问“p 是什么”，再问它指向的对象有什么限定。const int *p 与 int const *p 是同一种常见写法；int * const p 让 p 自身成为只读对象，因此定义时通常就需要给出目标。const int * const p 同时限制这两层。给形参的指针本身加顶层 const，主要约束函数体内的局部形参副本，不会冻结调用者的指针变量。

### 只读视图不等于不可变化

例子中 view 不能用于赋值，但 n 可通过原名字更新，随后从 view 读取应观察到 n 的值。这适合表达“这个函数不应通过此入口写输入”，不能证明别处没有写入。如果注册一个只读 DMA 接收缓冲区，硬件仍可能更新它；还要描述 DMA 所有权、访问时点和缓存维护。真正 const 对象即使被链接器放在可写 RAM，也不能合法强转后修改。

```c
int n = 3;
const int *view = &n;
int * const owner_view = &n;
n = 8;                 /* 合法，*view 现在为 8 */
*owner_view = 9;        /* 合法 */
/* *view = 4; */        /* 约束违例 */
/* owner_view = 0; */   /* 约束违例 */
```

### 为什么 int ** 不能随意变 const int **

如果允许这种转换，就能经由二级指针把一个真正 const 整数的地址塞进原来的 int *，随后通过这个可写指针尝试修改它，破坏类型保护。因此只读字符串数组接口要认真设计每一层，如指针数组元素是否能改、字符串内容是否能改；不要为了消除告警强制转换。对于嵌入式查找表，还应通过 map 文件确认实际只读段，而不是从关键字猜地址。

### 连续追问

**1. C 中 const int n=4 能当所有编译期常量吗？**

不能把 C++ 规则照搬过来。以 C11/C17 为前提，普通 const 对象一般不属于整型常量表达式，函数内用它定义数组可能得到变长数组。枚举常量或合适宏更适合需要整数常量表达式的位置。

**2. const 和 volatile 能同时用吗？**

可以，例如软件只读但硬件会改变的状态寄存器，可用 const volatile 描述“本代码不可写、访问不能按普通稳定对象处理”。实际地址、合法读宽度和读副作用仍由芯片手册规定。

**3. 给 memcpy 的源参数加 const 是否保证无副作用？**

只能约束该参数所指数据的普通写入方式，不保证函数不改全局变量、不写目的区或不调用外部服务。接口的可重入性与所有权应另行说明；const 不是纯函数声明。

### 容易答错的地方

- 把 const 指针读作“指向的地址位于只读区”：类型限定和链接地址是不同层次。
- 用强转去掉所有告警：可能把本来可诊断的接口错误变成运行时未定义行为。

### 动手验证

为四种单级限定写最小声明，逐一注释掉不合法赋值并观察诊断；再用两个源文件比较 C 与 C++ 对文件作用域 const 的链接行为。

### 查阅依据

- [SEI CERT C: EXP40-C. Do not modify constant objects](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/expressions-exp/exp40-c/)
- [WG14 N1570: Committee Draft, Programming languages — C (2011)](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

## C-03 · 小整数相加、负数与无符号比较为什么会出意外？

方向：通用 / MCU / Linux；难度：进阶；关键词：整数提升、溢出、未定义行为

### 面试官可能这样问

uint8_t 相加的表达式是什么类型？为什么 -1 小于 size_t 变量的判断可能为假？int 最大值加一会固定回绕吗？

### 考查意图

逐步做整数提升和通常算术转换，区分有定义的无符号模运算、实现定义转换和未定义行为。

### 30—60秒口述参考

先看参与运算前的提升，再看混合类型的共同类型，最后看赋值转换，不能只盯接收变量。在常见 32 位 int 平台，两个 uint8_t 通常先提升成 int，相加可以得到 300，再赋回 8 位无符号数才取模。有符号溢出在 C11/C17 中是未定义行为；无符号运算按范围取模。涉及长度和分配时，先验证输入范围与乘加是否溢出。

### 逐步推导而不是猜二进制

假设 CHAR_BIT 为 8 且 int 为 32 位，a、b 都是 uint8_t，值分别为 200 和 100：a+b 在 int 中得到 300；若赋给 uint8_t，结果才变为 44。若换成 16 位 int 平台，某些 uint16_t 表达式会转成 unsigned int，行为又不同。uint8_t 本身是可选的精确宽度类型，题目应先说目标平台确实提供它。

### 长度边界在运算前检查

常见错误是先算 count*sizeof(*p)，得到回绕后的小值，再检查是否超过预算。正确思路是用除法先判断上界，并把零大小政策写清。带符号的外部长度要先拒绝负数，再转成 size_t，否则负数转换后可能成为极大正数；事后加一个强转不会恢复丢失的含义。

```c
#include <stdint.h>
#include <stddef.h>
int array_bytes(size_t count, size_t item, size_t *out) {
    if (!out || item == 0 || count > SIZE_MAX / item) return 0;
    *out = count * item;
    return 1;
}
```

### 未定义行为改变的是推理资格

有符号 int 的最大值加一不是语言保证的“变成最小值”。优化器可利用有效程序不会发生该溢出的前提，因此依据溢出后的比较来检测溢出并不可靠。移位、越界和未排序副作用也可能形成未定义行为。未指定行为则是标准允许多个选择，不一定要求实现记录；实现定义行为需由实现说明，三者要分开回答。

### 连续追问

**1. 为什么 -1 < sizeof buffer 可能是假？**

sizeof 的结果是 size_t，通常是无符号类型。在常见 ABI 的通常算术转换下，-1 会变为这个无符号类型的最大值，于是比较为假。要先验证有符号输入非负，再按已确认范围转换，不能靠调整比较符号蒙混过去。

**2. unsigned 回绕有定义就可以用在长度里吗？**

不可以把语言有定义等同业务正确。协议序号可能有意使用模运算，但内存分配长度回绕会分配不足并导致越界。应记录有意回绕的场景，对其余长度运算设置明确上界。

**3. 开启 UBSan 能证明没有溢出吗？**

它可发现被实际执行且有插桩覆盖的许多未定义操作，但不是全部路径证明；无符号回绕通常也不是标准意义的 UB。仍需边界测试、输入约束、静态分析和目标平台上的类型宽度核对。

### 容易答错的地方

- 认为给结果变量换成 64 位就会让前面的 32 位乘法自动变宽：通常必须在运算前改变操作数类型。
- 用一次运行出现的回绕结果作为 C 标准结论：优化级别与实现可能改变现象。

### 动手验证

在独立测试工程打印 sizeof(int)、sizeof(size_t) 和 UINT_MAX，列出 200+100、-1 与 size_t 比较的转换步骤；对分配长度函数测试零、边界和边界加一。

- [SEI CERT C: INT31-C. Ensure that integer conversions do not result in lost or misinterpreted data](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/integers-int/int31-c/)

## C-04 · 数组和指针有什么区别，返回局部数组为何危险？

方向：通用 / MCU / Linux；难度：基础；关键词：数组退化、生命周期、边界

### 面试官可能这样问

char a[16] 和 char *p 能否互换？数组传入函数后 sizeof 为什么不再是 16？把局部缓冲区指针放进消息队列会怎样？

### 考查意图

同时检查对象类型、表达式转换、容量与所有权，识别异步场景中的生命周期错误。

### 30—60秒口述参考

数组是连续元素组成的对象，指针是保存地址的对象；多数表达式中数组会转为首元素指针，但 sizeof 数组和取数组地址等有例外。函数参数写成数组形式通常会调整为指针，因此容量要显式传递。返回自动存储期数组的地址，或把它交给延后执行的任务，都会在函数退出后失效。应让调用者提供存储，或者明确动态分配和释放责任。

### 地址相同并不表示类型相同

a 在多数表达式中得到指向首元素的 char *，而 &a 是指向整个数组的 char (*)[16]；数值地址可能一样，但加一的步长不同。指针变量 p 的 sizeof 是指针自身大小，不是目标缓冲区大小。数组不能像普通指针变量那样整体赋值；结构体中内嵌数组则会随结构体赋值复制，这是另一条规则。

### 把容量带进接口

示例只复制已经知道长度的字节序列，不依赖源以零结尾；要求源目标不重叠，且源至少有 len 个可读字节。接口把容量和实际长度分开，检查后补字符串终止符。真实工程还应约定失败时目的区是否保持不变，以及二进制数据是否根本不该走字符串接口。

```c
#include <stddef.h>
#include <string.h>
int copy_text(char *dst, size_t cap, const char *src, size_t len) {
    if (!dst || !src || cap == 0 || len >= cap) return 0;
    memcpy(dst, src, len); /* 前提：两个区域不重叠 */
    dst[len] = 0;
    return 1;
}
```

### 异步队列会延长使用时间

函数返回后局部自动数组的生命周期结束，不管栈上的旧字节是否看起来还在。若队列只复制一个指针，消费者拿到的只是失效地址；若队列确实复制指定长度的数据，则可在发送成功返回前完成所有权转移。要阅读队列 API，不能凭“发送消息”四个字判断是否发生深拷贝。静态数组虽然活得久，却引入复用覆盖、并发和不可重入问题。

### 连续追问

**1. 数组末尾后一个指针能不能用？**

可以构造同一数组的尾后指针用于循环边界与合法比较，但不能解引用它。再向外走、对无关数组指针随意相减也不能作为可移植 C 的写法；索引验证应在形成危险地址之前完成。

**2. 二维数组能直接传 int ** 吗？**

通常不能。连续二维数组退化后是指向一行数组的指针，而 int ** 指向指针对象，两种布局和解引用方式不同。接口可写明确列数的数组指针，或按一维连续存储显式传行列与步长。

**3. 改成 malloc 返回就完全正确吗？**

只是延长了存储寿命，还需处理分配失败、长度溢出、谁释放、是否跨模块分配器以及异步取消。调用者拥有还是借用必须明确，不能用堆分配掩盖接口契约缺失。

### 容易答错的地方

- 把数组退化说成“数组本来就是指针”：这会误判 sizeof、步长和参数布局。
- 认为返回后栈地址没被覆盖就可以继续用：对象已经结束生命周期，字节碰巧保留不赋予合法性。

### 动手验证

分别观察 sizeof a、sizeof p、a+1 和 &a+1；再画出生产者返回、消费者取队列的时间线，注明队列复制的是指针还是完整数据。

- [SEI CERT C: DCL30-C. Declare objects with appropriate storage durations](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/declarations-and-initialization-dcl/dcl30-c/)
- [WG14 N1570: Committee Draft, Programming languages — C (2011)](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

## C-05 · 寄存器置位、清位和移位操作怎样写才可靠？

方向：通用 / MCU；难度：进阶；关键词：位运算、W1C、读改写

### 面试官可能这样问

请写设置第 n 位和清第 n 位的表达式。硬件状态寄存器写一清零时，为什么 reg |= mask 可能误清别的状态？

### 考查意图

把语言层的位宽与提升规则、总线访问宽度和寄存器副作用放到同一次判断里。

### 30—60秒口述参考

普通无符号数据的置位、清位可用或与掩码，但先验证移位量，并确保左操作数有需要的无符号宽度。对硬件寄存器不能直接套普通变量的读改写：W1C、读清零、保留位和专用置位清位寄存器各有语义。volatile 不会把读改写变成原子，也不会知道哪些位禁止写。我会先查寄存器说明，再选择一次写掩码或受保护的访问。

### 先明确运算宽度

在常见 32 位 int 平台，1 << 31 涉及有符号左移的表示范围，不应拿来构造最高位掩码。使用 UINT32_C(1) 并检查 n<32，可以把意图固定到至少对应的无符号常量语义。uint8_t 在按位取反前通常先提升成 int，若目标是只翻转一个字节，应明确最终截断并说明协议只使用低八位，别把提升后的值误当八位结果。

### 普通数据与 W1C 不同

设状态寄存器位零和位一都为一，但本次只处理位零。对 W1C 寄存器执行读、或位零、再写回，会把位一的一也写回，从而同时清除尚未处理的事件。若手册规定直接写一清除且其他位写零无副作用，应只写已处理位的掩码。若寄存器混合控制位、W1C 位和保留位，则必须按该寄存器专门设计写入值。

```c
#include <stdint.h>
#include <stdbool.h>
bool set_bit32(uint32_t *value, unsigned n) {
    if (!value || n >= 32) return false;
    *value |= UINT32_C(1) << n;
    return true;
}
/* 上例只处理普通、独占访问的 uint32_t 对象。 */
```

### 并发更新与验证

主循环和 ISR 同时更新普通内存标志字，分别 OR 不同位也可能互相覆盖。可以使用原子 fetch_or、保护临界区，或让唯一执行者负责写；对 MMIO 是否支持原子访问必须另查，不能盲用 CPU 独占指令。GPIO 若提供专用置位清位寄存器，往往可避免软件读改写。最后查看反汇编和逻辑分析仪波形，确认总线访问宽度与次数。

### 连续追问

**1. 无符号右移一定补零吗？**

对无符号整数是逻辑右移，结果按定义向低位移动。以 C11/C17 为前提，负有符号数右移的结果是实现定义；需要可移植位协议时应先选用合适无符号表示，并处理所需的符号扩展。

**2. 移位量等于类型位宽会怎样？**

即使是无符号类型，移位量为负或大于等于提升后左操作数的宽度都不合法。硬件指令可能截断移位量，但 C 编译器不承诺保留这种硬件行为，所以必须先做范围判断。

**3. C 位域适合描述外设寄存器吗？**

只有在明确依赖特定工具链布局和访问方式、并经过验证的设备头文件中才可接受。位域的分配顺序、对齐及生成读改写行为不宜作为跨编译器协议；普通驱动优先使用明确宽度和掩码。

### 容易答错的地方

- 认为 reg |= mask 是单次写：它通常包含读取旧值，并可能触发寄存器读副作用。
- 认为关闭中断就能防所有硬件竞争：DMA 和外设自己仍可能更新状态。

### 动手验证

写一个 W1C 寄存器的纯软件模型，演示处理位零时读改写误清位一；对 n=0、31、32 分别检查掩码函数，避免直接操作真实未知外设。

### 查阅依据

- [SEI CERT C: INT34-C. Do not shift an expression by a negative number of bits or by greater than or equal to the number of bits that exist in the operand](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/integers-int/int34-c/)
- [GCC: Volatiles](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html)

## C-06 · 把字节缓冲区强转为结构体或整数指针，有哪些风险？

方向：通用 / MCU / Linux；难度：进阶；关键词：对齐、严格别名、字节序

### 面试官可能这样问

收到一帧网络数据后直接写 *(uint32_t *)(buf+1) 读取字段，在电脑上能跑，为什么换 MCU 或打开优化可能出错？

### 考查意图

区分对齐、有效类型、字节序、越界和结构体填充，提出可移植解析方法而不是只加 packed。

### 30—60秒口述参考

强转只改变编译器看待指针的类型，不会补足对齐、对象寿命、数据长度或字节序。buf+1 可能不满足 uint32_t 对齐，访问还可能违反有效类型规则。协议解析应先检查长度，再按字节拼装指定端序，或 memcpy 到合法对齐的整数对象后转换端序。packed 是工具链扩展，可能生成低效或不支持的非对齐访问，也不能定义整个跨平台协议。

### 四道独立检查

先确认至少有四个可读字节，再看目标地址是否满足所需对齐，然后判断用这个类型读取对象是否被 C 的别名规则允许，最后解释四个字节按哪种端序表示数值。某处理器能处理部分非对齐指令，只能缓解硬件层问题，不能自动修复语言层 UB；某些多寄存器访问或设备内存仍可能有更严格限制。

### 明确端序的字节解析

示例要求 uint8_t、uint32_t 存在，p 指向至少四个字节，字段是小端。先转到 uint32_t 再移位，避免小整数先提升到有符号 int 后高位移位触发问题。若使用 memcpy 读取，则只能得到主机端序的对象表示，需要再转换协议端序。编译器常能把小尺寸 memcpy 优化成合适加载，不应先假定它一定很慢。

```c
#include <stdint.h>
uint32_t load_le32(const uint8_t p[4]) {
    return (uint32_t)p[0]
        | ((uint32_t)p[1] << 8)
        | ((uint32_t)p[2] << 16)
        | ((uint32_t)p[3] << 24);
}
```

### 结构体布局属于 ABI 契约

结构体成员之间和尾部可能有填充；直接把 sizeof(struct) 个字节发出去，会把填充和编译器布局带入协议，甚至泄漏未初始化的填充数据。若必须与固定硬件描述符共享布局，要显式使用规定宽度、对齐、偏移断言和工具链约束。memcmp 整个结构体也不等于逐字段比较语义相等，填充字节可能不同。

### 连续追问

**1. char 指针能查看任何对象吗？**

C 允许通过字符类型查看对象表示，因此可以把一个合法对象当字节序列读取；反过来把任意字符数组强转为任意类型读取，并没有对称的普遍许可。修改对象表示还可能产生目标类型的非法表示，需要额外约束。

**2. 禁用严格别名优化就解决了吗？**

它最多改变该编译器的一类优化假设，不解决越界、非对齐、端序或对象寿命问题，还可能隐藏可移植性缺陷。优先修正表示转换方式；若确需扩展，限定在小模块并记录编译选项。

**3. packed 结构体成员地址可以随便传吗？**

不可以。成员可能位于非自然对齐地址，取地址交给期望普通对齐指针的函数时，函数不一定知道它来自 packed 对象。可复制到对齐的局部对象再处理，并核对编译器诊断。

### 容易答错的地方

- 以 x86 测试成功证明 C 程序合法：硬件容错不等同标准保证。
- 用 union 或 packed 不加前提地宣称跨 C/C++ 都可移植：两种语言和扩展规则并不完全一致。

### 动手验证

解析字节 78 56 34 12，断言得到 0x12345678；把输入放到不同字节偏移，比较字节解析与强转版本的编译诊断、消毒器结果和目标反汇编。

### 查阅依据

- [SEI CERT C: EXP36-C. Do not cast pointers into more strictly aligned pointer types](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/expressions-exp/exp36-c/)
- [SEI CERT C: EXP39-C. Do not access a variable through a pointer of an incompatible type](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/expressions-exp/exp39-c/)

## C-07 · 怎样设计一个类型正确、能安全注销的 C 回调接口？

方向：通用 / MCU / Linux；难度：进阶；关键词：函数指针、回调、上下文生命周期

### 面试官可能这样问

驱动需要回调上层并携带用户数据，你会怎样声明接口？设备退出时注销回调，为什么还有可能访问已经释放的对象？

### 考查意图

识别函数类型不匹配和异步对象生命周期问题，能够说明回调上下文、重入与取消语义。

### 30—60秒口述参考

我会用明确函数原型加 void * 用户上下文，注册时检查参数，规定回调运行在 ISR 还是线程、能否阻塞、是否可能并发，以及数据只借用多久。函数指针必须指向兼容签名，强转不能修复调用约定。注销既要阻止新回调，又要等待或确认已经在途的回调结束，之后才释放用户上下文；只把函数指针设空不能自动撤销已经取走的调用。

### 把接口契约写在类型之外

typedef 可让回调签名清楚，但类型系统不会告诉使用者缓冲区在回调返回后是否有效、错误值代表什么或注册是否覆盖旧回调。示例将数据作为只读借用，长度独立提供；ctx 是调用者对象的地址，不是任何类型都可以随意解引用的通行证。使用方应转回注册时的正确类型，并确保该对象仍存活。

```c
#include <stddef.h>
#include <stdint.h>
typedef void (*rx_fn)(void *ctx, const uint8_t *data, size_t len);
struct rx_hook { rx_fn fn; void *ctx; };
/* data 仅在回调期间有效；并发与注销由实现单独保护。 */
void dispatch(struct rx_hook hook, const uint8_t *data, size_t len) {
    if (hook.fn) hook.fn(hook.ctx, data, len);
}
```

### 注销需要处理在途调用

线程甲复制 fn 和 ctx 后暂时被抢占，线程乙把注册表清空并释放 ctx，线程甲恢复后仍会调用旧副本。可以用同一锁覆盖生命周期、引用计数与等待、事件线程串行化等方式解决。若回调允许自注销，等待自身退出可能死锁，接口需明确延迟销毁或由事件循环完成最终释放。ISR 中通常不能调用会等待的注销函数。

### 类型和 ABI 错误不是告警噪声

把返回 int 的函数强转成返回 void 的回调，或省略实际需要的参数，调用时可能违反 C 函数类型规则。不同 ABI 对浮点参数、结构体返回值和可变参数还有不同传递方式，不能仅因寄存器数量碰巧相同就认为安全。C11/C17 中 f(void) 明确无参数，f() 声明通常是不提供参数信息，不应拿来回避原型检查。

### 连续追问

**1. 为什么不直接用全局变量传上下文？**

单实例时可能工作，但多设备、重入和单元测试容易互相污染。显式 ctx 能把状态归属和实例关系固定下来，也便于模拟替身；它仍需要生命周期管理，不能把短命局部对象地址注册为长期上下文。

**2. 回调里能打印日志和 malloc 吗？**

先看执行上下文。线程回调也要满足延迟和锁顺序约束；ISR 回调通常应只完成短小确定的动作，再投递事件。日志内部可能加锁或等待串口，通用分配器也未必可重入，不能只按函数名字判断。

**3. 如何防回调重新进入驱动？**

可明确禁止并断言，也可设计状态机和锁顺序支持。不要持有非递归锁调用外部回调后又允许它调用同一驱动接口；常见做法是在锁内保存稳定事件快照，释放锁后回调，并维持对象引用。

### 容易答错的地方

- 把函数指针强转当适配层：签名不兼容时需要真正的包装函数转换参数和结果。
- 注销只写 fn=NULL 就马上 free(ctx)：在途调用可能已经持有旧指针。

### 动手验证

画出分发与注销的两线程交错；实现一个同步事件循环版本，测试回调为空、回调自注销和设备销毁后不再回调三种情况。

### 查阅依据

- [SEI CERT C: EXP37-C. Call functions with the correct number and type of arguments](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/expressions-exp/exp37-c/)
- [SEI CERT C: DCL30-C. Declare objects with appropriate storage durations](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/declarations-and-initialization-dcl/dcl30-c/)

## C-08 · C 与 C++ 混合工程中 extern "C" 到底解决什么？

方向：通用 / MCU / Linux；难度：进阶；关键词：C++边界、ABI、所有权

### 面试官可能这样问

C 驱动要被 C++ 业务层调用，头文件怎么写？反过来让 C 调用一个 C++ 类，是否套上 extern "C" 就够？

### 考查意图

区分语言链接、对象模型和运行库要求，能够设计稳定且可测试的跨语言边界。

### 30—60秒口述参考

extern "C" 指定 C 语言链接，常见用途是让两边对函数符号和调用边界达成一致，但它不会把 C++ 类、异常、模板或容器变成 C 接口。共享头文件要在 __cplusplus 条件下加链接块，暴露 C 可表达的函数与不透明句柄。C++ 实现负责封装对象、捕获异常、转换错误，并提供配套释放函数。最后用匹配的工具链与运行库链接。

### 共享头文件只暴露稳定接口

C 编译器不认识 extern "C" 语法，所以必须条件编译。下面只展示接口，不承诺具体设备实现；返回非零错误码，创建成功才写出有效句柄。为了减少跨模块 allocator 与对象布局耦合，销毁由创建模块负责。共享库长期演进时，还应定义整数宽度、结构体版本或大小字段及线程安全约定。

```c
#ifndef SENSOR_API_H
#define SENSOR_API_H
#ifdef __cplusplus
extern "C" {
#endif
typedef struct sensor_handle sensor_handle;
int sensor_open(sensor_handle **out);
int sensor_read(sensor_handle *h, int *value);
void sensor_close(sensor_handle *h);
#ifdef __cplusplus
}
#endif
#endif
```

### 包装类而不是暴露类布局

C 不能直接理解 C++ 的构造析构、继承和虚函数对象布局。可在 C++ 源文件实现 sensor_handle，内部持有真正类对象；导出的自由函数转发成员方法。若启用异常，包装边界应捕获预期异常并转换为文档规定的错误码，避免异常穿越不知道如何展开的 C 调用链。若工程禁用异常，仍要通过显式失败路径保证资源被释放。

### 启动与链接同样属于边界

裸机 C++ 的全局构造通常依赖启动代码遍历初始化数组，不能只把 .cpp 编译进来却跳过运行库初始化。编译器、ABI、标准库和浮点调用约定也必须兼容。通常由 C++ 驱动程序完成最终链接，以带入所需运行库，但要核对裸机工程的规格文件和链接脚本。extern "C" 不能修复 hard-float 与 soft-float 不兼容。

### 连续追问

**1. C++ 函数都能加 extern "C" 吗？**

不能把模板、成员函数对象模型和重载集合直接当成普通 C API。最稳妥的是提供名称唯一的自由函数包装，参数只使用两边约定的简单类型或不透明句柄；具体编译器还可能有附加限制。

**2. C 用 free 释放 C++ 返回的对象可以吗？**

除非接口明确保证它由兼容 malloc 分配且没有析构需求，否则不可以。new 与 delete、malloc 与 free 必须配套，跨共享库还要关注不同运行库堆；导出成对创建销毁函数可明确责任。

**3. 编译通过但链接 undefined reference 怎么排？**

先比较头文件声明、定义和目标文件符号，用 nm -C 查看是否一边产生了 C++ 修饰名。再核对源文件是否参与构建、库顺序、可见性与 ABI，不能把所有未定义符号都归因于缺少 extern "C"。

### 容易答错的地方

- 认为 C++ 是完全兼容的 C 编译器：隐式转换、const 链接规则、对象生命周期等都可能不同。
- 认为加链接块就可以让异常安全跨 C 边界：异常传播与语言链接是不同问题。

### 动手验证

写一个 C 调用方和一个 C++ 包装实现，观察加链接块前后的符号；测试创建失败、重复使用已销毁句柄的接口防护和所有权说明是否一致。
