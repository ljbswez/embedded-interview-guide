# 内存布局与资源管理

建立栈、堆、静态区和缓冲区的预算、所有权与故障定位方法。

适用方向：MCU / RTOS 与嵌入式 Linux。难度标签是复习分层，问题为原创训练题，不代表公司实际面试题。

## MEM-01 · 一个变量到底在栈、堆还是静态区，MCU 与 Linux 有何不同？

方向：通用 / MCU / Linux；难度：基础；关键词：存储期、内存布局、虚拟内存

### 面试官可能这样问

局部变量一定在栈上吗？初始化全局变量为什么可能同时占 Flash 和 RAM？Linux 进程看到的地址能直接交给 DMA 吗？

### 考查意图

区分 C 的对象语义、编译器安排、裸机存储器和操作系统虚拟地址，避免背固定“五区图”。

### 30—60秒口述参考

C 主要规定对象的存储期、作用域与链接，不保证每个局部变量一定落栈。常见 MCU 把代码和只读数据放 Flash，已初始化可写数据在 Flash 有初值、运行时复制到 RAM，零初始化区在 RAM 清零；堆栈位置由链接与运行库约定。Linux 的地址通常是进程虚拟地址，映射和权限由加载器、内核及分配器共同决定，不能直接当物理或 DMA 地址。

### 先判断生命周期，再讨论放置

自动存储期对象在进入相应作用域时建立、离开时结束，动态分配对象从成功分配到释放，静态存储期对象贯穿程序运行。优化器可把不需要取地址的局部值留在寄存器或完全消除；局部 static 虽有块作用域，却不是每次调用重新创建。面试中先给出语言保证，再补充目标工具链的常见实现，比直接把关键字塞入固定区域准确。

### 裸机初始化需要可追踪的搬运

例如可写全局阈值初始为七，它在复位后必须得到七，因此通常既有镜像中的初值又有 RAM 运行位置。零初始化大数组通常不需要在镜像存同样多的零，但启动代码要清零对应范围；.noinit 等特殊区域是否保留取决于链接脚本、启动代码和复位类型。const 表能否留在 Flash，要看访问属性、链接规则和是否被优化。

### Linux 中把地址空间与物理占用分开

进程可有代码、共享库、匿名映射、文件映射和各线程栈等区域，不必排成教学图里的单一连续布局。malloc 返回可访问的虚拟地址，并不承诺整块物理连续；多线程堆还可能有多个 arena。用户态指针更不能直接写到设备 DMA 寄存器。驱动需要通过合适 DMA API 建立设备可用映射，并遵守缓存与生命周期契约。

### 连续追问

**1. 为什么 .bss 很大而固件文件没那么大？**

常见 ELF 用不占同等文件数据的节来描述零初始化空间，运行时再清零。因此文件体积不等于 RAM 峰值；查看节大小、加载段的文件大小与内存大小，再对照启动清零表才完整。

**2. 函数里的 static 是线程安全的吗？**

存储期长不代表访问安全。C 中多个线程同时修改同一普通 static 仍需要同步；C++ 对函数局部静态初始化有另外的语言规则，也不能推出后续读写自动受保护。

**3. MCU 没有 malloc 就没有堆吗？**

可以完全不启用通用堆，但 RTOS 或中间件仍可能提供自己的动态池。任务栈也可能从某个池动态申请。需要追踪实际分配来源，而不是只搜索标准 malloc 一个名字。

### 容易答错的地方

- 把链接脚本布局当 C 标准规定：换 ABI、优化和运行环境就可能失效。
- 用 ELF 文件大小直接估算 RAM：会漏掉零初始化区、任务栈、运行时分配与共享映射差别。

### 动手验证

在最小程序中放入自动变量、局部 static、可写初值和零初始化数组，比较优化前后符号与 map；在 Linux 用自己的进程 maps 对照映射类别。

- [GNU ld: Output Section LMA](https://sourceware.org/binutils/docs/ld/Output-Section-LMA.html)
- [Linux kernel documentation: The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)

## MEM-02 · 怎样给 RTOS 任务和中断栈定大小，水位值靠谱吗？

方向：MCU / Linux；难度：进阶；关键词：栈预算、中断嵌套、高水位

### 面试官可能这样问

某任务平时只用几百字节栈，现场却偶发 HardFault。你怎样估算栈大小，并证明新配置有足够余量？

### 考查意图

把静态调用深度、异常现场、库函数与动态路径合并成可验证的预算，理解观测工具的局限。

### 30—60秒口述参考

我会先确认栈单位、任务栈与异常栈的使用规则，然后按最深调用链、局部数组、间接调用、递归和浮点异常现场估算上界，再用压力测试的高水位交叉验证。高水位只说明已走过路径的使用情况，不是所有未来路径的证明。对可能破坏返回地址的溢出，还要加边界保护、故障记录与拒绝过大输入，不能只把栈翻倍就结案。

### 估算的是调用链总量

单个函数只用六十四字节并不代表整个任务只需六十四字节，调用者尚未返回时它的活动记录仍在。格式化日志、错误恢复和协议解析可能是峰值路径；编译器内联、寄存器溢出和优化级别也会改变帧大小。GCC 的 -fstack-usage 可生成单函数估计信息，但间接调用、递归、变长数组和动态栈调整需要人工补全，不能把每个函数最大值简单取最大。

### 分清 Cortex-M 的两套栈

以常见 Cortex-M3/M4 RTOS 端口为例，线程模式任务可能使用 PSP，处理模式通常使用 MSP；异常进入时被打断线程的基本现场会压到当时使用的栈，后续处理函数使用 MSP。具体调度端口保存哪些额外寄存器要读实现。嵌套异常与浮点扩展现场会增加需求，不能把所有中断成本重复塞入每个任务栈，也不能完全漏算任务被抢占的硬件帧。

### 水位、哨兵与防护共同使用

常见高水位实现检查预填充图案，能发现已覆盖的深度，却可能漏掉“预留了但未真正写入”的栈空间。栈溢出检查可能只在任务切换等时点执行，届时相邻对象已经受损。可在支持的 MPU 上设置保护区，结合运行时最深路径、日志峰值和故障寄存器记录；Linux 线程则核对线程栈限制及保护页，不套用 MCU 的字节预算。

### 连续追问

**1. 任务创建参数的 1024 一定是字节吗？**

不一定。一些 RTOS API 以栈元素或字为单位，移植层和封装接口也可能不同。应查所用版本函数声明与 StackType_t 大小，同时核对水位返回单位；单位错误常造成四倍量级的误判。

**2. 为什么加 printf 后才崩？**

格式化和输出路径可能增加栈、加锁、递归调用日志钩子或改变时序。先测具体库配置与调用路径，不应一概说 printf 固定消耗某个数字；减少日志可能只是隐藏缺陷。

**3. 递归能不能放进实时任务？**

要能证明最大深度、每层成本和最坏执行时间，并处理超限输入。若深度受不可信数据控制，通常改成有容量上限的显式工作栈更可审计，同时要计算这个工作栈本身的存储来源。

### 容易答错的地方

- 高水位还有余量就宣称永远不会溢出：测试可能没走到异常路径，图案扫描也有盲区。
- 把某平台栈向低地址增长当语言规则，或按栈增长方向猜溢出一定先破坏哪个对象。

### 动手验证

给一个包含错误打印的任务生成 .su 文件，画最深调用链；记录端口保存现场和中断嵌套层数，再设计能触发这些路径的压力测试清单。

### 查阅依据

- [GCC: Developer Options, -fstack-usage](https://gcc.gnu.org/onlinedocs/gcc/Developer-Options.html)
- [CMSIS-Core (Cortex-M): Core Register Access](https://arm-software.github.io/CMSIS_6/latest/Core/group__Core__Register__gr.html)
- [Arm ABI: Procedure Call Standard for the Arm Architecture, AAPCS32](https://raw.githubusercontent.com/ARM-software/abi-aa/main/aapcs32/aapcs32.rst)

## MEM-03 · malloc、realloc 和 free 的所有权应该怎样约定？

方向：通用 / MCU / Linux；难度：基础；关键词：所有权、realloc、失败路径

### 面试官可能这样问

函数申请了一块内存后在第三步初始化失败，谁负责释放？为什么 p=realloc(p,n) 会在失败时出问题？

### 考查意图

把资源申请、所有权转移、错误返回和销毁设计成完整协议，并处理整数溢出与零大小边界。

### 30—60秒口述参考

每次成功分配都应有明确唯一的释放责任；借用者只能在约定期限内使用，不能擅自释放。realloc 应先接到临时指针：正大小请求失败时原块仍有效，直接覆盖原指针会丢失它。成功后旧指针及其派生地址不应继续使用。多步初始化要按逆序释放已经成功取得的资源，失败返回时对象处于可说明的状态，并明确不使用零大小 realloc 的版本差异。

### 先写出四个时点

接口应说明谁创建、何时交出所有权、谁能借用、什么时候销毁。比如 open 成功才把句柄交给调用者，失败由内部清理已取得的资源；send 若只借用缓冲区，返回或完成回调才是可复用时点。不能一边说调用者负责释放，一边在某条失败分支内部偷偷释放而不告知，否则容易发生重复释放。

### 扩容既检查算术也保留旧状态

下面示例假设 *data 为 NULL 或由兼容分配器返回，*capacity 描述其可用字节，n 严格大于零。分配成功才同时提交指针和容量；失败原对象不变。真实数组还应先检查元素个数乘元素大小是否溢出。扩容成功可能移动存储，原先指向元素的别名与迭代指针必须重新建立。

```c
#include <stddef.h>
#include <stdlib.h>
int resize_bytes(unsigned char **data, size_t *capacity, size_t n) {
    if (!data || !capacity || n == 0) return 0;
    void *next = realloc(*data, n);
    if (!next) return 0;
    *data = next;
    *capacity = n;
    return 1;
}
```

### 失败路径要与正常路径同样可测

多资源初始化可以集中到清理出口，按逆序释放，或把每一步的所有者封装进小对象。给每个分配点注入一次失败，检查此前取得的锁、文件描述符、缓存和任务是否都被回收；泄漏不仅指堆内存。裸机分配器可能没有 Linux malloc 的线程安全保障，释放也不一定有实时上界，所以要把执行上下文纳入约定。

### 连续追问

**1. free 后把 p 设为 NULL 就消除悬空指针了吗？**

只能清掉这个变量的一份地址副本，其他别名仍然悬空。free(NULL) 本身允许作为无操作，但不能借此证明重复释放不存在；需要用所有权约束或受控引用管理消除重复拥有者。

**2. realloc 成功但地址没变化，旧别名能继续用吗？**

接口设计上应统一把成功 realloc 当作原对象已被替换，重新从返回指针建立派生地址，不依赖实现碰巧在原地扩容。这样也避免代码只在移动时才暴露错误。

**3. C++ 对象可以用 realloc 扩容吗？**

不能把一般 C++ 对象当裸字节块任意移动，它可能有构造析构、内部指针和不平凡移动语义。应使用适当容器或明确对象类型约束；C 字节缓冲区的方案不能无条件跨语言套用。

### 容易答错的地方

- 只检查 malloc 返回值，不检查分配长度乘法：溢出可能让成功的小分配掩盖危险。
- 把 realloc(p,0) 当跨版本统一的 free 写法：本题明确用 free 释放并拒绝零大小扩容。

### 动手验证

给两步分配的初始化函数加入第 N 次申请失败的测试替身，逐一失败并验证未泄漏；测试扩容失败时指针、容量和已有数据保持不变。

### 查阅依据

- [The GNU C Library: Changing the Size of a Block](https://sourceware.org/glibc/manual/latest/html_node/Changing-Block-Size.html)
- [The GNU C Library: Freeing Memory Allocated with malloc](https://sourceware.org/glibc/manual/latest/html_node/Freeing-after-Malloc.html)

## MEM-04 · 设备运行几天后内存下降，怎样证明是泄漏而不是缓存或碎片？

方向：MCU / Linux；难度：进阶；关键词：泄漏诊断、RSS、长期运行

### 面试官可能这样问

线上服务 RSS 持续上涨，或者 RTOS 剩余堆越来越少，你的定位顺序是什么？看见 free 被调用能排除泄漏吗？

### 考查意图

建立可证伪的假设，通过对象数量、活跃字节、峰值和可达性区分不同增长来源。

### 30—60秒口述参考

我先把指标分清：活跃申请字节、分配器保留空间、最大空闲块和 Linux RSS 不是同一件事。重复执行稳定业务周期，观察对象数量及申请释放差额是否持续增长，再按调用栈、模块和生命周期归因。主机端可用 LeakSanitizer 等工具，MCU 可记录有限分配追踪。缓存要有上限和回收策略；看到 free 或短时压力稳定，都不足以证明所有错误路径没有泄漏。

### 从可重复业务周期采样

先固定输入、连接数和运行阶段，区分初始化预热与稳定期；每完成一轮连接建立断开，采集活跃对象数、总申请量、总释放量和当前字节数。若每轮净增一个对象，优先查断线、超时、重试、取消和异常退出路径。若活跃字节稳定而最大可用块持续缩小，则更像碎片或分配器布局问题，下一步的证据不同。

### Linux 的 RSS 不是堆账本

分配器可能保留空闲块供后续复用，free 后 RSS 未下降不一定代表对象仍被程序拥有；文件映射、线程栈、共享库和共享页也影响 RSS。可结合自己的进程 smaps 分类观察，并把对象分配追踪与实际驻留内存分开。共享页的统计口径还会影响跨进程相加结果，不应只凭系统总内存曲线给某个模块定罪。

### 工具报告是证据，不是免责证明

LeakSanitizer 常在进程结束等时点检查无法到达的分配；仍被全局容器引用、但业务上永远不用的对象可能属于逻辑泄漏而不被同样报告。AddressSanitizer 的目标主要是非法内存访问，运行环境和配置决定可用能力。MCU 跟踪记录本身要限长，避免为了查泄漏引入新泄漏；记录申请点编号、大小、所有者和释放事件比无界字符串日志更可控。

### 连续追问

**1. 没有 MMU 的 MCU 怎么查？**

在可替换分配入口统计当前与峰值用量，给分配块或外部账本记录固定编号，压力测试结束后列出未释放项。要保护追踪数据自身的并发访问，并评估插桩改变实时性的影响；也可把纯业务模块移到主机上测试。

**2. 缓存占着内存算不算泄漏？**

有明确上限、命中价值和回收策略的缓存通常是设计占用。若键空间无限增长、过期项不清或失去容量约束，即使指针全部可达也会耗尽资源，应按业务层泄漏或无界增长处理。

**3. 修好一处后怎样验收？**

保留最小复现和故障注入，让正常、超时、取消、重复关闭都经历多轮；比较修复前后的净增长斜率及峰值，而不只看某次结束还有多少空闲。还要检查修复是否变成提前释放。

### 容易答错的地方

- 把 RSS 不下降直接等同 malloc 泄漏：分配器保留、映射和共享页会影响它。
- 只统计次数不统计大小和失败申请：一次大块泄漏可被许多小块释放次数掩盖。

### 动手验证

在本地测试程序实现“有界缓存、真泄漏、分配后释放”三个独立模式，比较对象账本与工具报告；不要对不属于自己的生产进程做侵入式实验。

### 查阅依据

- [Clang: LeakSanitizer](https://clang.llvm.org/docs/LeakSanitizer.html)
- [Linux kernel documentation: The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)
- [Clang: AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html)

## MEM-05 · 为什么剩余内存很多却申请失败，内存池真的没有碎片吗？

方向：MCU / Linux；难度：进阶；关键词：外部碎片、内存池、确定性

### 面试官可能这样问

堆显示还有十六 KB，却申请不到连续四 KB，可能是什么原因？改成内存池会有哪些收益和代价？

### 考查意图

从分配形态和最坏延迟推导策略，区分内部碎片、外部碎片及容量耗尽。

### 30—60秒口述参考

总空闲量不等于最大可分配连续块，变长分配和交错释放可能把空间切碎；还需检查对齐、元数据和可用区域限制。固定块池能减少特定尺寸请求的外部碎片，并让路径更可预测，但会有块内浪费、类别失配和池耗尽。是否适合实时任务，要测最坏分配释放时间及锁竞争，不能只说 malloc 慢、内存池快。

### 用布局解释失败

想象连续空间中长寿命小块与短寿命大块交错。大块被释放后空闲总量很大，但被仍存活的小块隔开，无法满足更大的连续请求；合并算法只能合并物理相邻空闲块，不能随意搬动 C 指针指向的活动对象。块头、对齐填充和分配器的最小拆分单位也会影响可用容量，不能把用户请求大小直接与裸剩余字节一一对应。

### 固定块池把问题变成配额管理

例如为短消息准备若干六十四字节块，分配可以从空闲链表取块，释放放回，避免任意尺寸切割。但十字节消息也占一整块，是内部碎片；一个类别耗尽时其他类别空闲不一定能借用。设计时应统计尺寸分布、峰值并发数和长期占用，区分关键控制消息与大体积日志，必要时为关键流量保留独立配额。

### 具体实现仍需审计

FreeRTOS 的 heap_4 是可合并相邻空闲块的通用堆实现，不等于固定块池，也不承诺没有碎片。选择方案时应核对所用版本与端口，并评估临界区、链表遍历、对齐和失败返回。自建池还必须防止重复释放、释放外来指针和链表破坏；若把“空闲链表指针”放在空闲块里，使用后越界写可能直到下次分配才爆炸。

### 连续追问

**1. 内存池是不是一定常数时间？**

简单固定块空闲链表的取还操作可以有固定步骤，但锁竞争、缓存未命中、中断屏蔽和统计钩子仍影响延迟。多尺寸池搜索、扩容或跨池回退更不一定是常数时间，要对具体实现给界。

**2. 如何选择块数量？**

按最大在途请求、消费者最长阻塞时间、重试保留量和突发流量估算，再用压力测试验证。平均吞吐不能代替峰值并发；还应定义满池时丢弃、背压或降级策略，不能死等到高优先级任务阻塞。

**3. 能不能整理堆把小块搬走？**

普通 C API 直接暴露地址时，分配器不知道所有别名在哪里，不能透明移动活动块。使用可更新句柄、间接表或专门可移动对象系统才可能压缩，但复杂度与实时成本不同。

### 容易答错的地方

- 把总空闲字节当最大单块容量：碎片、对齐和区域约束会使两者明显不同。
- 宣称内存池零碎片零失败：它可能浪费块内空间，也可能因配额不足耗尽。

### 动手验证

设计长寿命与短寿命交错分配序列，记录总空闲和最大空闲块；再用固定块池模拟同样消息分布，比较峰值浪费和满池处理。

## MEM-06 · 越界、重复释放和 use-after-free 为什么常在别处崩溃？

方向：通用 / MCU / Linux；难度：进阶；关键词：越界、UAF、故障证据

### 面试官可能这样问

程序在 free 或链表遍历时崩溃，是分配器或链表库坏了吗？怎样从“最终爆炸点”追到第一次非法写？

### 考查意图

理解内存破坏的延迟显现，能够保存证据、缩小时间窗口并选择合适检测手段。

### 30—60秒口述参考

崩溃位置经常只是首次使用已损坏数据的地方，根因可能是更早的越界写或释放后访问。我会保留出问题的固件与符号、输入序列和线程时序，先判断地址属于哪个对象，再用主机消毒器、硬件观察点、边界哨兵或 MPU 缩小首次破坏的范围。修复要针对长度或生命周期协议，并验证失败路径，不能仅在最后解引用前加空指针判断。

### 三个典型传播路径

缓冲区多写一个字节可能损坏邻接长度或堆块头，分配器直到下一次合并才发现；释放后的对象被新分配复用，旧指针写入会破坏一个看似无关模块；重复释放可能让空闲结构形成环，直到后续分配才死循环。因此“在哪个函数崩”与“谁第一次写坏”不是同一个问题，日志时间线和地址归属比凭模块名猜更重要。

### 把监测点放到更早的位置

在主机可移植部分开启 AddressSanitizer，利用其报告的访问点、分配点和释放点建立因果链；对未对齐和算术等问题可结合 UBSan。工具不一定能覆盖裸机外设、未插桩库或任意 DMA 写。MCU 上可对已知被改坏的字设置硬件数据观察点，必要时用保护区让越界更早触发，但要注意硬件比较器数量和支持的访问宽度。

### 恢复之前保留诊断材料

记录固件标识、异常状态、相关栈范围和对象编号，不要在已损坏堆上继续 malloc 拼大日志。现场复位可以恢复业务，却会清掉证据，需设计有限且可信的持久或保留区记录。建立最小复现后，再通过长度校验、明确所有者、取消等待或索引边界修复。测试应同时覆盖恰好满容量、空数据、超长数据和取消后迟到回调。

### 连续追问

**1. 指针不是 NULL 为何仍非法？**

非空只说明数值不等于空指针，它可能已经释放、越界、未对齐、指向不可访问区或不是该类型对象。合法性来自对象与访问权限的生命周期契约，不能用一条 p!=NULL 代替。

**2. 给结构体加魔数可以彻底防 UAF 吗？**

不能。旧内存可能被覆盖成同样魔数，读取魔数本身也可能已是非法访问。它适合作为辅助诊断或受控句柄表校验，但不能替代所有权、代际编号和同步释放。

**3. 为什么开调试日志后不复现？**

日志改变内存布局、执行时序和线程交错，可能让错误地址暂时无害或减少竞争窗口。保留发布优化条件，使用低侵入跟踪和可控调度复现，不要因为加日志后稳定就认定修好了。

### 容易答错的地方

- 在崩溃点补 try-catch 或空判断就算根治：普通非法内存访问不是可靠可恢复的业务异常。
- 认为检测工具没报错就没有问题：它受路径、插桩范围、平台和运行时长限制。

### 动手验证

在专门的小测试程序中分别构造单字节越界与释放后访问，读取消毒器的三处调用栈；写出真实项目中能捕获首次破坏的最低侵入证据方案。

### 查阅依据

- [Clang: AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html)
- [Clang: UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)

## MEM-07 · 单生产者单消费者环形缓冲区为什么还需要同步？

方向：通用 / MCU / Linux；难度：深入；关键词：环形缓冲区、发布协议、SPSC

### 面试官可能这样问

串口中断写环形队列、任务读取，head 和 tail 各只有一方写，是否就完全不需要原子或屏障？队列满了怎么办？

### 考查意图

从索引与数据的发布顺序推导并发协议，说明单生产者单消费者的前提及扩展边界。

### 30—60秒口述参考

各写一个索引减少了竞争，但读对方索引和发布数据仍需要正确同步。在 C11 线程模型下，可用原子索引：生产者先写槽位，再 release 发布 head；消费者 acquire 看到 head 后读数据，完成后发布 tail。还要定义满空判定与回绕。ISR 版本需核对原子实现可中断使用；多生产者、DMA 或无界覆盖不能直接沿用同一证明。

### 先规定容量和所有权

一种易解释的方案是使用 N 个槽位并始终空出一个，head==tail 表示空，next(head)==tail 表示满，因此有效容量为 N-1。生产者只修改 head，消费者只修改 tail；一个槽位从空闲变为生产者私有、已发布、消费者私有，再回到空闲。每次读写都应归属于这个状态转换，而不是只考虑索引数学。

### 两条方向相反的同步链

生产者先完整写槽位，再发布新的 head；消费者观察到发布后才读取，防止先看到索引却看到旧内容。消费者读完后发布 tail；生产者确认释放后才复用槽位，防止覆盖尚在读取的数据。单核无缓存 MCU 也不能自动跳过编译器层面的约束。Linux 内核有自己的并发 API 与内存模型，不能把内核的宏直接当成用户态 C11 接口。

### 满队列和零拷贝都要补协议

若满时拒绝写，生产者必须能上报丢包或施加背压；若选择覆盖最旧数据，就等于生产者也改变消费边界，原本各写一个索引的证明已经失效。零拷贝接口返回槽位指针时，消费者必须显式归还，不能更新 tail 后继续持有指针。对 DMA，还需额外处理缓存和硬件完成事件，原子索引不负责搬运或刷新数据。

### 连续追问

**1. 容量为二的幂有什么好处？**

可用与掩码代替取模，但这只是索引运算优化，并不解决同步。要静态或运行时验证容量是二的幂，同时说明索引表示、保留空槽还是单调计数，避免混用不同满空公式。

**2. 两个生产者能共用这个队列吗？**

不能仅把 head 改成原子自增就宣称正确，因为抢到槽位与完成写入是不同事件，发布顺序可能出现空洞。应外部串行化生产者或采用经过证明的多生产者算法，并重新讨论进度与满队列行为。

**3. 为什么有些实现把 head 和 tail 分开对齐？**

在多核缓存系统上，两方频繁写同一缓存行可能形成伪共享，增加一致性流量。分离缓存行是性能设计，不是正确性必要条件；缓存行大小需按目标确定，不能把 Cortex-M7 的数值套给所有 Linux 平台。

### 容易答错的地方

- 把 head、tail 都加 volatile 当并发证明：它没有建立跨线程发布关系。
- 满时悄悄移动 tail 仍宣称原 SPSC 方案不变：索引写入者与所有权已经改变。

### 动手验证

在纸上逐步走 N=4 的空、写三项、满、读一项、回绕；对每次槽位访问标注所有者，并写出两个发布方向的同步关系。

- [GCC: Built-in Functions for Memory Model Aware Atomic Operations](https://gcc.gnu.org/onlinedocs/gcc/_005f_005fatomic-Builtins.html)

## MEM-08 · 如何给资源紧张的设备做内存预算与降级策略？

方向：MCU / Linux；难度：深入；关键词：内存预算、峰值并发、资源上限

### 面试官可能这样问

只有有限 RAM，却要跑通信、升级、日志和多个任务。你怎样给出可信的内存预算，保证高峰期不会互相拖垮？

### 考查意图

把静态布局、动态峰值、区域限制与失败处置放进同一资源模型，体现可交付的工程判断。

### 30—60秒口述参考

我会按实际内存区域列静态段、任务与中断栈、动态池、DMA 缓冲区和升级临时区，再按能同时发生的业务场景计算峰值，留出可解释余量。总字节够不代表某个 DMA 可达区域或最大连续块够。为队列、连接、日志和重试设置上限与满载行为，用分配失败注入和长时间压力测试验收；不能依赖内存耗尽后所有模块自己恢复。

### 预算表需要反映放置约束

同一 MCU 可能有主 SRAM、紧耦合 RAM、保留区和外部 RAM，它们对 CPU、DMA、缓存及低功耗保留的能力不同。把所有容量相加再比较总需求，会掩盖某一区域早已超额。对每一类对象记录大小、数量、对齐、生命周期、所在区域和访问主设备；链接阶段可固定的项目用脚本断言，运行期部分使用高水位和池统计补足。

### 峰值来自可重叠的业务场景

升级解压、TLS 握手、日志积压和传感器采样可能同时出现。预算不是把每个模块平均占用相加，也不是无脑叠加所有理论最大值，而是根据状态机明确哪些峰值能够重叠、哪些被互斥策略排除。若设计规定升级时暂停某类采样，就要在代码与测试里验证这个约束；文档中的“应该不会同时发生”不算容量保证。

### 先规定超限后保留什么能力

重要控制任务可使用预留池，日志采用有界缓冲并记录丢弃数，网络入口在达到上限时拒绝或背压，重试必须有次数和保留量限制。错误报告自身不能无限申请内存，否则耗尽时连诊断也失效。Linux 用户态还要考虑进程或容器限额、映射和按需分配导致的驻留增长；申请成功不代表以后触达所有页都不会遭遇系统资源压力。

### 连续追问

**1. 余量留百分之多少才够？**

没有通用百分比。余量应对应估算误差、未覆盖路径、版本演进和观测分辨率，另加已识别的突发需求。给出具体测量与边界条件比背一个固定比例更可信，关键系统还需专门的最坏情况论证。

**2. 能不能运行时共享一大块缓冲区节省 RAM？**

可以，但要让状态机保证用途不重叠，并把借用与归还写进接口。升级和通信共用区若仍有异步 DMA 或回调未结束，切换用途就会破坏数据；互斥业务必须包括在途操作，而不仅是主线程状态。

**3. 如何让预算随版本持续有效？**

持续集成比较 map 中区域占用及大对象变化，保存压力测试峰值，并为新增连接数、协议缓存或任务设置评审阈值。发现增长先解释来源，不仅修改上限让构建通过。

### 容易答错的地方

- 把空闲 RAM 当任意设备都能访问的连续缓存：区域可达性、对齐和缓存属性可能不同。
- 耗尽时继续无上限重试申请：会扩大排队与日志压力，妨碍关键任务恢复。

### 动手验证

给一个假设的采样设备列出五类对象和最坏并发场景，明确两个不得重叠的用途及代码保证；为每类资源写出耗尽时的返回、降级和诊断行为。
