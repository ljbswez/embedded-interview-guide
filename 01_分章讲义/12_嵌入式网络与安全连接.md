## NET-01 · TCP 为什么会“粘包”？UDP 保留边界是否就不需要协议设计？

方向：Linux；难度：基础；关键词：TCP、UDP、字节流、分帧

### 面试官可能这样问

发送端连续 send 两条消息，接收端一次 recv 得到一条半。是不是 TCP 出错？如果换 UDP，是不是所有问题就消失了？

### 考查意图

考查传输语义与应用协议边界，能否明确完整性、可靠性和容量约束。

### 30—60秒口述参考

TCP 提供有序字节流，不保留应用的 send 调用边界，所以一条消息拆成多次读取或多条消息一次读出都是正常行为。应用要自己分帧，例如固定长度、分隔符加转义或长度头。UDP 保留数据报边界，但不承诺送达、有序或不重复，过小接收缓冲还可能截断数据报。选协议应从时效、可靠性、连接管理和网络条件出发，而不是把换 UDP 当处理 TCP 分帧的捷径。

### 边界属于哪一层

TCP 的分段、重传、接收缓冲和读取长度都会改变每次 recv 看到的字节数量，应用不能把抓包中的单个 TCP 段当成完整业务消息。即便某次本机测试每个 send 都对应一个 recv，换延迟、负载或缓冲大小后仍可能改变。

一种教学协议可以使用固定宽度长度头加负载。接收方先累计完整头部，校验长度在上限内，再累计负载；一次读取若包含多帧就连续消费，末尾不足部分保留到下一轮。长度字段必须定义字节序及是否包含头部，不能只说“前四字节是长度”就结束设计。

### 报文安全与资源边界

任何长度都来自不可信输入，先检查范围和加法溢出，再决定分配或等待。声明一个很大长度却一直不发送内容，会占用连接与内存，因此还应有最大帧长、组帧截止时间和每连接缓存限额。分隔符方案则要定义转义、编码和最大未闭合长度。

校验和或业务摘要有助于发现内容问题，但不能替代消息边界与资源上限。协议版本、消息类型、请求标识和可选字段兼容也应提前约定，否则以后扩展会依赖双方隐含的结构体布局。

### UDP 的取舍要说完整

UDP 常适合可丢弃、重时效的数据，若应用需要可靠命令，就要自己设计超时、序号、重试和去重等机制。较大数据报可能触发 IP 分片并增加损失影响，应结合路径 MTU 选择应用消息大小。零长度数据报是有效输入，不能照搬 TCP 的 EOF 规则将其认定为断线。

### 连续追问

**1. 关掉 Nagle 就不粘包了吗？**

不会改变 TCP 字节流语义。TCP_NODELAY 影响部分发送时机，但接收端仍必须处理任意分割和合并，不能用它作为分帧机制。

**2. TCP 可靠是否等于服务端已执行命令？**

不是。传输层确认只涉及协议栈层面的接收，业务解析、授权、执行和持久化需要应用层响应或事务标识。

**3. UDP 缓冲不足能下次接着读余下半包吗？**

不能按 TCP 思路处理，数据报可能被截断并丢失剩余部分。应选择足够缓冲并按接口检查截断标志，或在协议层限制大小。

### 容易答错的地方

- 将一次 send 与一次 recv 视为一一对应，正常分段就会破坏业务解析。
- 换成 UDP 后仍声称天然可靠，漏掉丢失、重复、乱序与分片风险。

### 动手验证

为长度头协议构造五种输入：头部拆开、负载拆开、两帧合并、非法超长、连接关闭时只剩半帧；逐一给出状态转移和错误处理。

## NET-02 · send 成功但长度不够怎么办？非阻塞发送队列如何避免丢数据和内存失控？

方向：Linux；难度：进阶；关键词：部分发送、背压、发送队列、MSG_NOSIGNAL

### 面试官可能这样问

网关上传数据时 send 返回正数，但小于请求长度。有人直接丢弃原缓冲，还有人一直原地重试。你会怎样改？

### 考查意图

考查部分完成、缓冲所有权和背压，能否把 API 返回值转成可靠状态机。

### 30—60秒口述参考

send 返回正数只表示这次接受了这么多字节，剩余部分必须从正确偏移继续发送。非阻塞遇到 EAGAIN 时保留队列和偏移，等可写再继续，而不是忙等或重发整帧。发送缓冲在完成或取消前必须保持有效；队列要有上限和业务背压策略。还要处理 EINTR、断线错误与 SIGPIPE，例如 Linux 可按调用使用 MSG_NOSIGNAL。数据进入本地协议栈不表示对端业务成功，重要命令另需应用确认。

### 偏移属于请求状态

每个待发消息可记录总长度、已发送偏移、请求标识和截止时间。发送返回 n 后只前移 n；重新从头发送会造成重复字节，而直接释放余下部分则会截断消息。多个线程写同一连接还可能在应用层交错，应由单一发送队列或严格串行化保证帧顺序。

缓冲若指向临时栈变量、已复用采样区或会被下一帧覆盖的内存，异步等待可写期间内容就可能改变。可以转移缓冲所有权、拷贝到有界队列或使用稳定引用，但必须说明何时释放以及断线时怎样完成失败通知。

### 什么时候关注可写

队列不空且暂时发不出去时才需要持续关注可写；队列清空就撤销该关注，避免普通可写套接字让事件循环不断醒来。一次事件只能做有限预算的工作时，还需在应用内部调度剩余任务，不能把所有公平性责任交给内核。

EINTR 后可按业务退出状态重试；EAGAIN 是等待条件，不是连接失败。其他错误应进入统一关闭流程，并让上层决定哪些请求可以重试。不能在收到错误后悄悄新建连接再重发所有字节，因为对端可能已经执行过部分完整消息。

```c
/* Linux 用户态非阻塞 socket 概念片段，非内核模块。
 * 省略函数封装、枚举定义和总截止时间检查；buf/offset 由队列持有。 */
while (offset < length) {
    ssize_t n = send(fd, buf + offset, length - offset, MSG_NOSIGNAL);
    if (n > 0) { offset += (size_t)n; continue; }
    if (n < 0 && errno == EINTR) continue;
    if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK))
        return NEED_WRITABLE; /* 保留偏移和缓冲，等待后续事件 */
    return FAILED;
}
return COMPLETE;
```

### 背压关系到产品语义

若传感器持续生产而网络长期变慢，无界发送队列会耗尽设备内存。要根据数据类型选择暂停采集、拒绝新请求、丢旧遥测或持久化补传；关键控制命令与可丢弃周期数据不应共用同一丢弃策略。

统计队列字节数、最老消息年龄、重试和丢弃数量，比只记录 send 调用次数更能解释现场吞吐。关闭服务时还要决定限时排空还是立即取消，不能永久等待不再可用的网络。

### 连续追问

**1. send 返回零应该无限重试吗？**

不应。对非零长度发送应结合具体接口视为没有进展并采取受控处理，避免死循环；状态机需要进展判据和总截止时间。

**2. 一次 send 就发一个小消息能省掉队列吗？**

仍不能假定完整发送或永不阻塞。简单程序可同步地维护剩余偏移，但事件循环和高并发场景通常需要显式保存待发状态。

**3. MSG_NOSIGNAL 能修复断线吗？**

不能，它只避免该发送触发 SIGPIPE 的默认进程终止风险。调用仍返回错误，连接和业务请求仍需恢复策略。

### 容易答错的地方

- 部分发送后重发整个缓冲，产生业务流中重复字节。
- 把缓冲交给非阻塞发送后立刻复用，导致实际发出的内容与入队时不同。

### 动手验证

用一个假发送接口按“发送三字节、EAGAIN、发送剩余”的顺序返回，检查偏移、队列容量和释放次数；该练习不需要真实外网。

- [send(2) — Linux manual page](https://man7.org/linux/man-pages/man2/send.2.html)
- [socket(7) — Linux manual page](https://man7.org/linux/man-pages/man7/socket.7.html)

## NET-03 · 非阻塞 connect 如何判断成功？可写事件为什么还必须查 SO_ERROR？

方向：Linux；难度：进阶；关键词：connect、EINPROGRESS、SO_ERROR、连接状态机

### 面试官可能这样问

连接服务器设置了非阻塞，connect 返回 EINPROGRESS。之后 poll 可写了，是否可以直接发送登录报文？超时怎么覆盖整个连接过程？

### 考查意图

考查连接完成与成功的区别，以及 DNS、地址尝试和连接对象代次的管理。

### 30—60秒口述参考

非阻塞 connect 立即返回零表示已经成功，返回 EINPROGRESS 表示建立过程正在进行。等待可写或相关错误通知后，要调用 getsockopt 读取 SO_ERROR，并检查调用本身及错误值，才能判断连接结果；可写通知本身不等于成功。连接超时由应用使用单调时钟和总截止时间控制，超时后取消并关闭对应尝试。解析地址、尝试不同地址、TCP 连接和 TLS 握手是不同阶段，各自预算应包含在整体业务期限内。

### 把连接过程建成有限状态

可使用解析中、连接中、传输已连接、TLS 处理中、业务可用和失败等状态。状态转换必须保留失败阶段和错误码，避免把 DNS 失败也统称为 connect 超时。套接字设置非阻塞只影响相应 I/O，不会让同步 getaddrinfo 自动变成非阻塞。

在 Linux 网络套接字中，异步连接完成后读 SO_ERROR 是常规判断方法。不要反复调用 connect 当作唯一轮询方式，也不要在失败后继续把同一个描述符当已连接对象用；失败尝试通常应关闭并按新尝试重建状态。

### 地址与截止时间

getaddrinfo 可能返回多个 IPv4/IPv6 地址，一个地址不可达不代表整个服务不可达。可按成熟地址尝试策略进行串行或有节制并行尝试，但所有尝试都应受全局预算和资源数量限制。不能对每个地址都重新给予完整长超时，把用户预期几秒变成很久。

EINTR、调度延迟及事件循环忙碌都会消耗剩余预算。采用绝对截止时间，收到事件后重新核算是否超时；计时通常用单调时钟，而证书有效期等现实时间问题另行处理。

### 取消和迟到通知

一旦连接被取消，其待处理事件仍可能已经进入应用队列；描述符关闭后数值又可能复用。连接对象应有所有者、状态及代次，不让旧超时回调关闭新连接。成功转换也只能发生一次，防止超时与完成事件同时到达时重复通知。清理还应撤销事件关注与计时器，剩余回调发现终止状态时只做幂等退出。

### 连续追问

**1. SO_ERROR 为零就能认定业务上线吗？**

只能说明这一层连接结果成功。TLS 认证、协议登录、授权或订阅仍可能失败，应由更上层状态继续判断。

**2. socket 的发送超时能覆盖整个异步连接吗？**

不能用一个选项替代所有阶段的期限。具体选项对阻塞调用与等待接口的影响不同，事件循环应明确维护自己的截止时间。

**3. 失败后立刻无限重连会怎样？**

可能放大服务端故障和耗尽本机端口、CPU或电量。应分类错误，使用带抖动的退避和最大并发，并保留可观测原因。

### 容易答错的地方

- 收到可写事件就发送登录，漏掉连接被拒绝等同样会唤醒的结果。
- 每次事件或地址重试都重置完整超时，导致总等待远超业务约定。

### 动手验证

画出连接完成与超时同一轮到达的时序，规定谁能提交最终状态；再为双地址失败写出统一截止时间下的处理步骤。

- [connect(2) — Linux manual page](https://man7.org/linux/man-pages/man2/connect.2.html)
- [getaddrinfo(3) — Linux manual page](https://man7.org/linux/man-pages/man3/getaddrinfo.3.html)

## NET-04 · 拔网线后为什么连接还显示 ESTABLISHED？怎样定义断线和重连？

方向：Linux；难度：进阶；关键词：TCP超时、心跳、半关闭、幂等重试

### 面试官可能这样问

设备断网后很久才报错，业务人员要求立刻重连。TCP keepalive、应用心跳和业务超时应该怎样配合？

### 考查意图

考查本地连接状态与端到端存活的差别，以及重试是否会重复执行业务。

### 30—60秒口述参考

本地 TCP 状态并不能即时证明远端或网络仍正常，静默中断时没有新报文就可能暂时缺乏失败证据。keepalive、重传超时和 TCP_USER_TIMEOUT 等机制处理不同层面的存活条件，业务仍应有自己的响应截止时间或心跳。收到流的 EOF 表示对方发送方向结束，RST 与超时又是不同现象。重连需要有界退避、重新认证及会话恢复；未确认请求是否已经执行必须通过请求 ID 和幂等协议解决，不能直接盲重发。

### 区分四类失联现象

正常 FIN 表示有序结束一个发送方向，应用可以在消费完已接收数据后处理半关闭；RST 常导致立即可见的连接重置错误；黑洞丢包可能需要等重传或业务截止时间；远端进程卡死还可能让 TCP 协议栈继续应答，但业务不再返回。

因此“还能 ping 通”或“连接仍是 ESTABLISHED”都不能证明业务可用。心跳应经过真正关注的应用处理链，携带必要会话信息，并定义连续失败阈值，避免把瞬时抖动直接当永久离线。

### 各类超时回答不同问题

系统 TCP keepalive 的启用、探测间隔和次数需要按目标环境确认，默认配置往往不符合每个产品的需求。Linux TCP_USER_TIMEOUT 约束特定未确认或因零窗口未发送数据的持续时间，也不是一个对空闲连接定时调用业务的心跳。

应用响应超时应使用单调时钟，并区分连接、登录和单请求期限。超时太短造成误判与重复操作，太长拖慢恢复；要结合链路时延、功耗、流量成本和控制命令时效，明确风险取舍。

### 重连成功不是事务完成

断线可能发生在服务端执行命令之后、回包到达之前。这时客户端不知道结果，盲目再发“增加一次”会重复执行。可用稳定请求标识、服务端去重结果或读取最终状态的方式恢复，具体保留窗口与持久性必须协议化。

重连退避加入抖动可避免大量设备同时冲击服务，网络恢复时仍需重新解析、认证和恢复订阅。积压数据按业务分类决定补传、合并或丢弃，避免过期控制命令在网络恢复后突然生效。

### 连续追问

**1. recv 返回零以后还可以 send 吗？**

TCP 允许半关闭，能否继续发送由协议状态和对端行为决定。不能把读方向 EOF 简化为所有方向立即失效，也不能无限发送。

**2. 心跳越频繁越好吗？**

会增加功耗、流量与服务负载，也可能在短暂拥塞时误判。应让检测时间满足业务要求，并给出成本与误判率的权衡。

**3. 重试同一请求 ID 就必然幂等吗？**

还需要服务端按 ID 持久或按约定窗口去重，并返回一致结果。客户端自己复用 ID 而服务端完全不检查，不能形成保障。

### 容易答错的地方

- 把 TCP 连接状态当远端业务健康状态，漏掉应用挂死和路径黑洞。
- 重连后无条件重放所有控制指令，可能重复执行或执行已经过时的动作。

### 动手验证

模拟“服务端执行成功但响应丢失”，设计客户端下一步查询或重试协议；列出正常关闭、RST、黑洞和业务卡死各自的观测证据。

## NET-05 · 为什么不能直接发送 C 结构体？DNS 和 IPv4/IPv6 解析要处理哪些边界？

方向：Linux；难度：基础；关键词：字节序、序列化、DNS、getaddrinfo

### 面试官可能这样问

同一协议在 x86 测试正常，换 ARM 后字段错位；另外设备用 IP 能连，用域名却失败。两类问题分别怎么定位？

### 考查意图

考查表示层与寻址层的清晰分工，能否避免依赖本机布局和单一地址族。

### 30—60秒口述参考

线上的消息格式必须明确字段宽度、字节序、对齐、编码与版本，不能直接发送本机结构体，因为填充、位宽、位域和浮点表示等细节可能不同。网络序通常指大端，使用合适转换或逐字节编解码。域名解析由 getaddrinfo 等接口按环境返回地址列表，应检查解析错误、地址族与服务端口，正确释放列表并尝试适当候选。DNS 成功不保证 TCP 或 TLS 成功，能用 IP 连接也不说明域名、证书身份和解析配置都正确。

### 把结构体当内存布局而非线格式

同样几个成员的结构体在不同 ABI 中可能有不同填充，直接发出去还可能泄漏未初始化字节。packed 属性最多改变部分布局，不自动解决字节序、非法未对齐访问或协议演进。更稳妥的是对固定宽度字段显式序列化，并逐个验证范围。

接收时不要把任意字节指针强转成结构体指针就读取，除了长度还要考虑对齐和语言规则。多字节字段可以复制到合适对象后转换，或通过字节运算组装；对字符串明确编码与长度，不依赖发送方恰好附带零终止符。

### 解析需要独立错误通道

getaddrinfo 的返回值使用自己的错误域，应按该接口解释，而不是对所有失败只打印 errno。设置合理的 hints，保留返回的 sockaddr 长度和地址族；不能只取第一个 IPv4 地址并把其余忽略，尤其在双栈或多地址部署中。

域名解析受本地配置、缓存、搜索规则和网络可达性影响，DNS 常用 UDP 但也需要处理 TCP 等协议规定的情形，不能宣称它永远只发一个 UDP 包。产品中同步解析可能阻塞事件线程，需选择合适的线程或异步解析架构并管理超时。

### 用 IP 测试的结论要有限

直接 IP 测试可帮助区分寻址和连通性，但 HTTPS/TLS 的服务器身份通常仍以原始目标名称校验，随意改用 IP 可能改变证书匹配与 SNI 行为。缓存地址也要有更新和失效策略，不能首次解析成功后永久固定，忽略服务迁移。

### 连续追问

**1. htonl 能转换所有整数吗？**

它处理相应宽度的整数，不能拿来转换任意结构体、浮点或任意 64 位字段。应根据协议定义选择宽度和转换方法。

**2. 大小端一样就能直接发结构体吗？**

仍有填充、对齐、位宽和编译选项等差异，且接口难扩展。明确线格式比依赖碰巧相同的 ABI 更可靠。

**3. 域名解析失败应该无限立即重试吗？**

不应。应区分临时失败与无效名称，限制重试频率并使用总预算；缓存和退避策略也要考虑网络切换与配置更新。

### 容易答错的地方

- 通过 packed 就宣称跨平台协议完成，漏掉字节序和数据表示。
- 忽略 getaddrinfo 返回码和地址列表，只对一个固定地址族写死逻辑。

### 动手验证

设计包含版本、长度、序号和温度值的线格式，用十六进制例子手工编解码；再为解析失败、IPv6 不通但 IPv4 可达写出候选地址处理流程。

## NET-06 · MQTT QoS 2 就代表业务只执行一次吗？断线后怎样恢复消息与会话？

方向：Linux；难度：进阶；关键词：MQTT、QoS、会话、业务去重

### 面试官可能这样问

设备通过 MQTT 下发开锁命令，团队认为用 QoS 2 就绝不会重复执行。你同意吗？保留消息、离线会话和重连又分别意味着什么？

### 考查意图

考查协议交付范围与业务事务边界，能否区分保留状态、会话存续和消息确认。

### 30—60秒口述参考

按 MQTT 5.0，QoS 0、1、2 分别提供相应协议范围内的至多一次、至少一次和恰好一次交付语义，不能直接推出整个业务数据库或物理动作恰好执行一次。发布端到代理、代理到订阅者是不同传递关系，实际订阅 QoS 和会话状态也影响结果。关键命令仍应有业务 ID、有效期、幂等或状态确认。保留消息表示主题上的最近保留状态，不是任意历史队列；会话和消息过期需要按版本及代理配置明确。

### 先限定 QoS 的作用范围

QoS 1 允许重复，应用不能看到 PUBACK 就认为订阅端业务已经执行；QoS 2 通过协议交换避免对应交付重复，却不把远端执行动作和持久化自动变成原子事务。订阅者收到消息后崩溃在“执行完成、业务记录未落盘”的窗口，仍需应用级恢复规则。

若命令改变现实世界状态，优先定义目标状态或可去重的命令 ID，并给出查询结果的接口。诸如“设置为关闭”可能更易重复执行，而“再推进一步”需要更强的序号和已执行记录；具体设计取决于设备行为，不是换个 QoS 数字即可解决。

### 保留消息、遗嘱与会话分开看

保留消息可让新订阅者收到某主题最近的保留值，适合状态快照，但将短时控制命令作为保留消息可能让后来上线的设备误执行旧命令。遗嘱是异常断开等条件下的通知机制，触发时机还受保持连接与会话设置影响，不是即时电源检测。

MQTT 5.0 的 Clean Start、Session Expiry Interval 和 Message Expiry Interval 分别关联会话建立/保留与消息有效期。与 MQTT 3.1.1 的配置名称和语义应区分，不能把一个客户端库的选项映射成所有版本统一概念。

### 重连与资源限制

需要稳定管理客户端身份，处理会话是否实际恢复、是否需要重新订阅及尚未完成的协议交换。设备端和代理端都要限制未确认消息和缓存容量，网络断开较久时按过期规则清理，避免复连后集中执行陈旧指令。

TLS、主题授权和载荷校验是另外的安全层；知道主题名不等于有权控制设备。日志应关联业务 ID 与协议状态，既能排查重复，也避免打印密钥或敏感载荷。

### 连续追问

**1. QoS 2 一定是最佳选择吗？**

不是，它增加交换与状态成本。允许丢弃的遥测、需要至少一次的状态和关键控制有不同需求，应结合业务容忍度与资源预算选择。

**2. retained 消息是不是离线消息队列？**

不是同一概念。保留值服务于主题最近状态，离线会话中的待交付消息依赖会话及 QoS 等条件，不能互相替代。

**3. 更换 Client ID 有什么影响？**

可能无法恢复原会话和未完成状态，也可能留下旧会话占用资源。客户端身份应按部署和会话生命周期设计，不能每次启动随意变化。

### 容易答错的地方

- 把协议级 QoS 2 宣传成物理动作和业务数据库的端到端恰好一次。
- 保留无有效期的动作命令，导致新上线订阅者执行历史控制操作。

### 动手验证

用“命令到达、动作执行、结果持久化、应答发送”四步画断电窗口，设计业务去重与过期字段；示例用于协议推演，不代表任何真实门锁项目。

### 查阅依据

- [MQTT Version 5.0 — OASIS Standard](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)

## NET-07 · 设备时间不准导致 TLS 失败，能否关闭证书校验？正确验证包含哪些环节？

方向：Linux；难度：进阶；关键词：TLS、证书、时间、服务身份

### 面试官可能这样问

新设备没有准确时间，HTTPS 连不上。有人建议跳过证书校验解决量产启动问题，你会给出什么替代设计？

### 考查意图

考查加密与认证的区别，以及设备初始可信状态、时间引导和证书维护的闭环。

### 30—60秒口述参考

不能把关闭校验作为正式修复，加密通道如果没有验证对端身份仍可能连接到错误或被冒充的服务器。TLS 验证应结合可信根、证书链、用途、有效期和预期服务身份，并按库接口检查结果；SNI 只影响选择服务，不替代名称验证。设备需设计可靠时间来源或安全的初始时间引导，以及信任库和证书更新。TLS 1.3 的协议能力也不自动解决业务重放、密钥保存和系统时钟问题。

### 验证的不是“有没有一张证书”

证书链需要连接到设备信任的锚，签名有效还不代表适用于目标服务。应使用实际期望的主机名或按规范表达的 IP 身份进行匹配，不能把 DNS 返回的任意名称、证书展示名或用户未经确认的输入当信任依据。

还需检查证书用途、关键扩展和有效期等条件，具体由所选 TLS 库及配置提供实现。不要手写一个只比较 Common Name 的简化验证器；现代身份校验有明确规则，应让成熟库执行并在配置上确认已启用。

### 时间与信任的启动难题

设备刚上电可能只有错误的墙上时钟，证书因此被判断尚未生效或已过期。方案可结合有质量的 RTC、受保护的最近可信时间以及经过安全设计的时间获取路径；未经认证的时间数据不能直接成为攻击者任意回拨校验窗口的工具。

如何获取首个可信时间依赖产品威胁模型和硬件能力，没有通用一句“先连网络校时”就完成的答案。应明确初始信任材料来源、时间异常时允许的有限功能、恢复与更新流程，避免为了上线方便永久放宽全部认证。

### 长期维护与业务安全

信任根、服务证书和客户端凭据都有生命周期，产品应支持受控更新与吊销相关策略，记录可诊断错误但不泄漏私钥。双向 TLS 中服务端和客户端各有验证职责，设备证书也要和业务授权关联，不能仅握手成功就允许所有命令。

TLS 1.3 的早期数据存在重放方面的限制，不能未经设计承载非幂等操作。应用读写也可能出现需要继续等待读或写的状态，应通过库的状态机处理，而不是把一次 TLS 写入想当然地等同于一次底层 send。

### 连续追问

**1. 只验证 CA，不验证域名够吗？**

不够。受同一可信 CA 签发的其他服务证书也可能通过链验证，需要把证书身份与预期服务名称绑定。

**2. 证书固定能替代全部更新机制吗？**

不能。固定策略会引入证书或密钥轮换、备用和恢复要求，配置错误可能使整批设备断联；必须规划生命周期。

**3. 系统单调时钟能验证证书有效期吗？**

通常不能直接替代现实时间。单调时钟适合持续时间和超时，证书日期判断需要可信的墙上时间及相应验证策略。

### 容易答错的地方

- 把跳过校验作为量产配置，保留加密却失去对端身份保障。
- 只设置 SNI 就认为完成名称验证，混淆服务选择与认证。

### 动手验证

列出新设备第一次联网的信任材料与时间来源，并分别处理过期证书、错误主机名、未知根和时钟回拨；不要通过关闭验证让测试“变绿”。

- [RFC 9525: Service Identity in TLS](https://www.rfc-editor.org/rfc/rfc9525.html)
- [RFC 5280: Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile](https://www.rfc-editor.org/rfc/rfc5280.html)

## NET-08 · “偶尔网络慢”怎样分层定位？抓包、socket 状态和业务日志各证明什么？

方向：Linux；难度：深入；关键词：网络排障、吞吐、尾延迟、TCP窗口

### 面试官可能这样问

设备上传偶尔慢十倍，服务端说链路正常，应用说 send 没报错。你如何用证据判断瓶颈在哪一层？

### 考查意图

考查观测链和可证伪假设，避免把所有性能问题都归于带宽或网络协议。

### 30—60秒口述参考

先明确“慢”的定义，是解析、连接、TLS、发送入队、传输还是业务响应变慢，再记录同一请求的分阶段时间与字节量。结合 socket 状态、发送接收队列、重传、窗口和抓包判断传输行为，同时检查应用背压、线程调度和服务端处理。send 成功只说明本地接受数据，单端抓包也不能证明端到端业务完成。实验应固定版本与负载、控制变量，先验证假设再调整缓冲或协议选项。

### 先拆开一条请求的耗时

以请求 ID 关联 DNS 开始结束、连接结果、握手、入队、实际发送进度与应用响应时间。各机器时钟不一致时不能直接比较绝对时间，应优先用各自单调时钟测时长并利用协议事件关联。日志采样要有界，否则为测性能加入大量同步打印反而改变结果。

同时区分吞吐与延迟：大批量上传总带宽正常，不保证控制命令尾延迟低；队列里积压很多旧数据会让实时命令等待。产品可能需要分级队列、流量预算或独立连接，而不是单纯把一个发送缓冲调大。

### 传输层证据怎样解读

重传说明报文或确认未按预期完成，但原因可能是链路丢失、拥塞或其他路径问题，需要结合两端和时间线。接收窗口收缩或零窗口提示对方接收侧压力，应用不读取也会让 TCP 表现为“网络慢”；本地队列持续增长则提示生产速度超过消费能力。

ss 可观察连接与队列等信息，具体统计字段依工具和内核版本而异。抓包应注明采集位置，网卡卸载功能可能改变看到的分段和校验表现，不能把主机抓包中的每个异常标记都直接认定为线上损坏。

### 设计最小对照实验

先固定协议、消息大小和并发，分别测本地回环、同网段与目标路径，逐步加入 TLS、持久化和业务处理，以隔离增量成本。负载测试要在授权测试环境进行并限制速率，不能为排障直接对生产端发无界流量。

调整 TCP_NODELAY、缓冲大小或并发前写出预期现象：如果假设是小包等待，就说明哪个阶段会下降；如果是接收不及时，加大发送缓冲可能只延后暴露问题。验证通过后保留回归用例和性能预算，避免一次偶然改善被当根因。

### 连续追问

**1. 丢包率为零能排除网络导致的慢吗？**

不能。时延抖动、排队、流控、DNS 或握手等待都可能影响体验；还要核对测量路径与业务路径是否一致。

**2. 服务端回复了 ACK 就代表数据库已提交吗？**

TCP ACK 只对应传输层，应用事务完成需要业务响应及其语义定义。定位时不要用低层确认替代高层完成。

**3. 抓到重传就应该立即调大超时吗？**

先查原因与业务预算。放大超时可能减少报错却恶化恢复时延，并不修复拥塞、接收背压或应用阻塞。

### 容易答错的地方

- 只报告平均带宽，不观察队列年龄和高分位响应时间，漏掉用户真正感知的慢。
- 一次调整多个网络参数，结果变好也无法说明哪个假设成立。

### 动手验证

为一次上传写六个阶段计时点及对应证据，建立“应用队列过长、接收端不读、连接超时”三种假设，每种设计一个可区分的只读观察。
