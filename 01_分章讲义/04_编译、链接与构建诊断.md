# 编译、链接与构建诊断

读懂从源码到 ELF 的证据，用链接脚本、符号和反汇编定位工程问题。

适用方向：MCU / RTOS 与嵌入式 Linux。难度标签是复习分层，问题为原创训练题，不代表公司实际面试题。

---

## BUILD-01 · 预处理、编译、汇编、链接分别做什么，报错应从哪层查？

方向：通用 / MCU / Linux；难度：基础；关键词：构建流程、宏、诊断分层

### 面试官可能这样问

同一份源码在同事机器能编译，你这里提示类型错误或 undefined reference。你会如何沿构建流程定位，而不是反复清理重编？

### 考查意图

理解每阶段输入输出与信息边界，用中间产物验证头文件、宏、代码生成和符号解析假设。

### 30—60秒口述参考

预处理展开头文件与宏、选择条件编译；编译进行语义检查和优化并生成目标相关代码；汇编形成目标文件及符号重定位信息；链接组合对象、选择库成员、解析符号并按布局生成镜像。我先保留实际完整命令和工具链版本，用 -E、-S、-c 等观察阶段产物，再根据诊断层次检查原因。链接器找不到符号与编译器看不到声明是两类问题。

### 每一层的证据不同

头文件找错或宏把表达式改坏，先看预处理结果，而不是阅读未展开源码猜。类型或原型不一致通常在编译层暴露；语法正确并不代表定义已经被构建。目标文件可以保留未解析引用，直到链接阶段才需要相应定义。某些 LTO 流程会把更多优化和诊断推迟到链接时，但这种实现变化不影响按证据区分阶段的基本方法。

### 用最小命令保留中间结果

示例假设本机已安装 GCC，在独立目录有无外部依赖的 sample.c；命令只生成该测试目录下文件。MCU 应改用对应交叉编译器并带上与项目一致的宏、包含路径和目标选项，否则得到的汇编可能属于主机。需要复现时，构建系统打印出的实际命令比 IDE 面板里的简化配置更可靠。

```sh
gcc -std=c11 -Wall -Wextra -E sample.c -o sample.i
gcc -std=c11 -Wall -Wextra -S sample.c -o sample.s
gcc -std=c11 -Wall -Wextra -c sample.c -o sample.o
gcc sample.o -o sample
```

### 宏错误要从展开后的表达式解释

函数式宏可能重复计算有副作用的参数，运算优先级也可能因缺少括号改变。即使给参数和整体都加括号，也不能消除重复求值；适合时优先用有类型的 static inline 函数。条件编译还可能让一边看到结构体某个字段、另一边看不到，造成跨翻译单元布局失配。要记录编译定义，不能只对照头文件文本。

### 连续追问

**1. include 一个头文件是不是把实现也链接进来？**

头文件主要通过预处理参与当前翻译单元，通常只提供声明或内联定义；库实现仍需编译和链接。若头文件直接放普通外部定义，多个源文件包含又可能导致重复定义，不是解决缺符号的稳妥方式。

**2. 为什么编译成功但链接缺库？**

编译器只需知道调用的类型和声明，目标文件可记录未解析符号。最终链接才寻找定义；应核对目标文件是否参与、库路径与顺序、条件编译及符号名称，而不是无根据地修改函数原型。

**3. 清理重编什么时候有意义？**

当怀疑依赖追踪不完整、配置变化未传播或混入旧对象时有意义，但要保留失败证据并查清依赖缺陷。若只靠每次清理才能构建可靠，构建系统本身仍需修正。

### 容易答错的地方

- 把所有报错统称编译错误并盲加 include：链接阶段未定义符号通常不是缺声明。
- 认为加括号的宏就完全安全：参数重复求值仍可改变状态或触发 UB。

### 动手验证

构造一个只声明未定义的函数和一个参数重复求值的宏，分别观察在哪个阶段出问题；保存真实构建命令及预处理产物，解释两类故障的证据差异。

### 查阅依据

- [GCC: Options Controlling the Kind of Output](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)
- [The C Preprocessor: Macro Pitfalls](https://gcc.gnu.org/onlinedocs/cpp/Macro-Pitfalls.html)

## BUILD-02 · ELF、BIN、HEX 的区别是什么，section 和 segment 又有什么不同？

方向：通用 / MCU / Linux；难度：进阶；关键词：ELF、重定位、镜像格式

### 面试官可能这样问

为什么 ELF 文件比 BIN 大很多？只把 ELF 头去掉就等于 BIN 吗？Linux 加载器和链接器分别更关注哪些结构？

### 考查意图

区分文件元数据、链接组织和运行时装载视图，能够使用工具验证地址、大小和符号。

### 30—60秒口述参考

ELF 可包含代码数据、符号、重定位、调试信息和装载描述；BIN 通常只是按转换规则铺排的原始字节，不自带完整地址与符号；HEX 用带地址和校验的文本记录表示镜像。section 主要服务链接组织，segment 描述装载视图，一个装载段可覆盖多个节。不能直接去掉 ELF 头当 BIN，转换还涉及可加载内容、地址空洞和 LMA 等规则。

### 同一文件有不同观察视角

编译后的可重定位对象常保留节、符号和尚待解决的重定位；最终可执行 ELF 会组织需要装载的段，同时可能保留供调试使用的节。调试符号通常不需要烧进 MCU 的可执行 Flash 区，所以 ELF 大并不直接意味着固件占用大。Linux 加载器主要依程序头设置映射和权限，不需要按照每个源码函数单独映射。

### 文件字节数与运行空间要分开

某个加载段的内存大小可大于文件大小，例如运行时需有零初始化区域而不必在文件存同等数量的零。裸机工具转换到原始 BIN 时，地址间空洞可能被填充，导致文件异常变大。应查看各节的运行地址、装载地址和属性，再核对烧录器把文件写到哪里；BIN 没有通用入口与基址信息，必须从外部约定取得。

### 先读头，再读节、段、符号与重定位

readelf -h 查看架构、类型和入口，-S 查看节，-l 查看装载段，-s 查看符号，-r 查看重定位。nm 能从符号角度快速找定义与引用，objdump 可把代码和重定位联系起来。对 MCU 使用匹配的交叉工具或确认工具支持该架构；带调试信息的 ELF 应与发布镜像一同留档，以便之后解析现场地址。

```sh
arm-none-eabi-readelf -h -S -l firmware.elf
arm-none-eabi-readelf -s -r firmware.elf
arm-none-eabi-nm -n firmware.elf
```

### 连续追问

**1. BIN 比 ELF 小就说明优化成功了吗？**

不一定，可能只是去掉符号和调试元数据，实际可加载代码完全没变。比较代码和只读数据段、加载内容及运行时 RAM，才能判断优化对象；不能比较不同格式的总文件大小下结论。

**2. HEX 的校验能保证固件可信吗？**

普通记录校验主要用于发现传输或存储差错，不等同加密认证与安全启动。签名、版本回滚策略和可信启动链属于另外的完整性与信任设计，不能由文件格式名字推导。

**3. 什么是重定位？**

目标代码可能引用尚未确定地址的符号，重定位项描述链接器或动态加载器需要如何修补相应位置。它不是任意把固件搬到新地址就能运行的保证；绝对地址、向量和外设映射仍有约束。

### 容易答错的地方

- 把 section 和 segment 混成同一个表：会误解链接布局与加载器行为。
- 直接截掉 ELF 文件头去烧录：正文并不是单一连续、无需解释的程序字节流。

### 动手验证

对同一测试固件比较 readelf 的节表与程序头，再查看转换所得 BIN/HEX；解释调试节、零初始化区和地址空洞分别影响哪一个大小指标。

### 查阅依据

- [GNU Binary Utilities: readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)
- [GNU Binary Utilities: nm](https://sourceware.org/binutils/docs/binutils/nm.html)

## BUILD-03 · 链接脚本怎样让 .data 在 Flash 存初值、在 RAM 运行？

方向：MCU；难度：进阶；关键词：链接脚本、VMA、LMA、初始化

### 面试官可能这样问

请解释 .data 的运行地址和装载地址。把函数段放到 RAM 后为什么上电仍然会崩？链接脚本会自动把内容搬过去吗？

### 考查意图

建立链接脚本与启动代码之间的契约，理解符号、区域、对齐、保留段和运行时复制。

### 30—60秒口述参考

VMA 是链接后代码或数据运行时采用的地址，LMA 是镜像中装载内容的位置。常见裸机 .data 的 VMA 在 RAM、LMA 在 Flash，启动代码按链接器提供的边界复制，再清 .bss；脚本本身不会执行拷贝。RAM 函数同样需要内容已搬入、目标存储器可用且必要时完成缓存同步。区域大小、对齐和保留入口应通过脚本及 map 验证。

### 符号是两端共享的边界约定

链接脚本可导出装载起点、运行起点和结束地址，启动代码据此计算长度。链接器符号通常表示一个地址或数值，不一定是实际分配了存储的 C 变量；C 端声明与取地址方式要符合工具链约定。复制目标若是外部 RAM，必须先完成其硬件初始化，且初始化过程不能反过来依赖那块尚不可用的数据区。

### 读懂一段最小布局片段

示例仅解释 GNU ld 的 .data 和 .bss，假设 FLASH、RAM 区域已经定义；不是完整芯片脚本。向量表、只读段、异常展开表、构造数组、栈堆保留及芯片专用段还要由完整工程处理。NOLOAD 不等于上电自动保留或清零，真正行为取决于加载和启动路径。

```text
.data : {
  . = ALIGN(4);
  _sdata = .;
  *(.data .data.*)
  _edata = .;
} > RAM AT> FLASH
_sidata = LOADADDR(.data);
.bss (NOLOAD) : {
  . = ALIGN(4);
  _sbss = .;
  *(.bss .bss.*) *(COMMON)
  _ebss = .;
} > RAM
```

### 布局正确还需要保留与边界检查

开启 --gc-sections 后，只被硬件入口引用、没有普通调用关系的向量或注册表可能需要 KEEP 等规则保留。用 MEMORY 表达可用区域，再结合 ASSERT 和实际栈堆预留检查重叠；只看 .bss 不超界会漏掉运行时栈。多 RAM 区域还要匹配 DMA 可达性与低功耗保留属性，不能把放置成功当作访问必然合法。

### 连续追问

**1. 为什么改 .data 初值后 BIN 增大？**

初值需要存在可加载镜像中，即使运行时变量位于 RAM；新增初始化数据可能同时增加 Flash 镜像与 RAM 占用。改成零初始化可能影响文件占用，但不消除运行时存储需求。

**2. 把变量放 .noinit 就一定能跨复位保留吗？**

不一定。脚本和启动代码须共同避开清零，芯片对应 RAM 在该复位或电源模式下还必须保留；内容也需有版本、校验和有效性判断，冷启动不能信任随机残留值。

**3. 为什么 RAM 函数搬完还可能执行旧指令？**

在带相关缓存或取指缓冲的平台，写入代码数据后可能需要规定的 cache 维护和指令同步；还需保证函数依赖的常量、跳转范围及被调用函数符合执行环境。M0 与 M7 的要求不能混说。

### 容易答错的地方

- 以为 AT> FLASH 会在运行时主动复制：它描述镜像布局，不是执行代码。
- 把链接器地址符号当普通已分配整数变量读取：可能实际读到该地址处的数据而不是边界值。

### 动手验证

在一份已知可启动的工程里追踪 _sidata、_sdata、_edata 与启动复制循环，核对长度和单位；只改一个可写初值，观察 map 和烧录镜像变化。

### 查阅依据

- [GNU ld: MEMORY Command](https://sourceware.org/binutils/docs/ld/MEMORY.html)
- [GNU ld: Output Section LMA](https://sourceware.org/binutils/docs/ld/Output-Section-LMA.html)
- [GNU ld: Input Section and Garbage Collection](https://sourceware.org/binutils/docs/ld/Input-Section-Keep.html)

## BUILD-04 · 固件突然变大或 RAM 超限，怎样读 map 找到增长原因？

方向：MCU / Linux；难度：进阶；关键词：map文件、尺寸分析、链接裁剪

### 面试官可能这样问

加了一个看似很小的日志调用，Flash 增加几十 KB。你如何找到是谁被拉进来，又怎样判断删减没有破坏功能？

### 考查意图

从区域到输出节、输入节、对象和库成员逐层归因，用同条件差分代替凭函数名猜测。

### 30—60秒口述参考

我会保存修改前后相同配置的 ELF 与 map，先分清是 Flash 加载内容、RAM 静态区还是调试元数据增长，再定位增长最大的输出节、输入对象与符号。map 可显示库成员为何被引入，nm 按大小列符号帮助收敛。日志可能带入浮点格式化、语言运行库或大常量表。任何裁剪都要核对保留入口、失败诊断与功能回归，不直接删除看起来不认识的段。

### 比较的条件必须一致

两次构建若一个带调试符号、一个没有，或优化级别、LTO、标准库不同，文件尺寸差可能与业务改动无关。记录编译器版本、完整链接命令、脚本和特性开关，确保先比较同一指标。Flash 中 .data 初值与 RAM 中 .data 运行空间不能算到同一个总量后混讲，零区和栈预留也应分开列。

### 沿 map 追到引入关系

先看 memory region 是否超限，再看对应输出节里哪个对象贡献最大。某个新调用可能使静态库成员整体加入，成员又引用浮点转换、锁或系统调用适配。GNU ld 的 map 和交叉引用信息可帮助追这条链，nm --size-sort 可找大符号，但被内联、合并或匿名常量的数据不一定对应一个醒目的函数名。

```sh
arm-none-eabi-gcc objects.o -Wl,-Map=firmware.map,--cref -o firmware.elf
arm-none-eabi-nm -S --size-sort firmware.elf
arm-none-eabi-readelf -S firmware.elf
# 第一行仅示意链接参数；实际工程仍需目标参数、库和链接脚本。
```

### 裁剪需要证明入口仍然存在

函数与数据分节配合 --gc-sections 能去除不可达部分，但硬件向量、反射式注册表或按链接区间扫描的对象可能没有普通引用边。必须用脚本保留和最终产物验证维护它们。压缩字符串、改变日志等级或关闭浮点格式化也可能影响故障诊断和业务精度，应结合真实需求选择，不能只追求最小数字。

### 连续追问

**1. nm 最大的函数就一定是主要增长点吗？**

不一定。增长可能来自许多小函数、常量表、对齐填充或库成员整体引入；还要比较修改前后增量，而不是只看最终排名。内联和 LTO 也会改变符号归属。

**2. text、data、bss 三项怎样看？**

它们是常见工具的分类汇总，具体归类与格式有关。对裸机常可粗看 text 与初值贡献镜像、data 与 bss 贡献静态 RAM，但最终要按实际节属性、LMA/VMA 和脚本检查，不能机械套公式覆盖所有布局。

**3. 用 -Os 就一定比 -O2 小吗？**

优化目标不同，但具体代码与工具链版本会影响结果，不能保证每个函数或每次构建严格更小。应实测尺寸、性能和栈变化，发布测试使用最后选定的同一配置。

### 容易答错的地方

- 用最大符号名单替代差分分析：它无法直接解释本次改动带来的增量。
- 看到未知节就放进 DISCARD：可能删掉向量、构造或异常展开等必要信息。

### 动手验证

在测试工程中分别加入整数与浮点格式化，比较同配置 map 的库成员引入链；整理一页“增长区域—对象—引用者—可接受替代”的证据。

### 查阅依据

- [GNU ld: Command-line Options](https://sourceware.org/binutils/docs/ld/Options.html)
- [GNU Binary Utilities: nm](https://sourceware.org/binutils/docs/binutils/nm.html)
- [GNU Binary Utilities: readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)

## BUILD-05 · static、extern、声明和定义怎样决定跨文件可见性？

方向：通用 / MCU / Linux；难度：基础；关键词：链接属性、static、extern、头文件

### 面试官可能这样问

头文件里写 int counter; 为什么新编译器链接报重复定义？改成 static 是否就解决共享问题？extern int counter=1 又是什么？

### 考查意图

分离作用域、链接属性与存储期，理解暂定定义和不同编译选项掩盖的问题。

### 30—60秒口述参考

文件作用域 static 通常让对象或函数具有内部链接，每个翻译单元独立；extern int counter; 常用于声明另处定义的对象，真正定义应在一个源文件中。C 文件作用域的 int counter; 是暂定定义，不是纯声明；多个文件通过头文件产生定义并不适合作为共享设计。extern 带初始化仍是定义。改成 static 可能让错误消失，却把一个共享计数器变成多份副本。

### 三个维度分别回答

作用域决定名字在源码哪里可见，链接属性决定不同声明是否指向同一实体，存储期决定对象活多久。块内 static 对象有静态存储期但名字只在块内可见；文件内 static 函数体现内部链接。不要把 static 一律翻译成“放静态区”，尤其函数根本不是普通数据对象，其机器码放置由编译链接安排。

### 头文件声明与源文件定义配对

示例中头文件只给外部声明，一个源文件提供初始化定义，使用者包含同一头文件获得类型检查。实现文件也应包含自己的公共头，避免声明定义逐渐漂移。若把 static counter 放头文件，每个包含它的翻译单元可能拥有各自状态，跨模块修改不会共享；这适合明确要求每单元副本的少数场景，不是修共享变量链接错误的默认办法。

```c
/* counter.h */
#ifndef COUNTER_H
#define COUNTER_H
extern unsigned counter;
void counter_reset(void);
#endif

/* counter.c：单独的源文件 */
#include "counter.h"
unsigned counter = 0;
void counter_reset(void) { counter = 0; }
```

### 暂定定义和工具链历史行为

C 中文件作用域无初始化的非 extern 对象声明可能形成暂定定义；某些历史工具链的 common 合并行为曾让多个文件误定义仍链接通过。GCC 的 -fno-common 会暴露此类重复定义，不能把改回 -fcommon 当长期接口修复。C++ 的规则又不同，命名空间作用域 const 的默认链接行为也不能无条件套回 C。

### 连续追问

**1. extern 声明会分配存储吗？**

常见的 extern int x; 只是声明，不单独提供定义；但 extern int x=1 带初始化时是定义。还应结合前序声明和作用域判断链接属性，不能仅凭一个单词概括所有情形。

**2. 头文件可以定义函数吗？**

可以有明确链接策略的内联定义，例如 C 头中常用 static inline 提供各翻译单元可见的小函数实现。普通外部函数定义放头文件会导致多定义风险；C 的 inline 与 C++、GNU 历史模式细节不同。

**3. 把共享变量改成访问函数有什么收益？**

可以集中同步、校验和实现隐藏，也便于以后修改表示。但函数包装本身不会自动线程安全，仍需内部锁或原子协议；返回内部可写指针又可能重新暴露封装。

### 容易答错的地方

- 把 extern 当“引用另一个文件的变量”而不检查是否有唯一定义：最终仍可能缺符号。
- 用头文件 static 消除链接错误后认为还是同一份状态：实际可能每个翻译单元各有副本。

### 动手验证

建两个源文件分别包含同一头，比较纯 extern 声明、暂定定义和 static 定义在 nm 与链接诊断中的差异；记录所用 GCC 的 common 选项。

- [GCC: Options for Code Generation Conventions](https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html)

## BUILD-06 · weak 默认中断为什么没被覆盖，静态库顺序又为什么重要？

方向：MCU / Linux；难度：进阶；关键词：weak、静态库、符号解析

### 面试官可能这样问

我在库里实现了一个强中断函数，最终还是进默认弱处理。或者交换 -lfoo 与目标文件顺序就能链接成功，这是怎么回事？

### 考查意图

区分符号优先级与归档成员是否被抽取，并考虑名称、可见性和段裁剪等不同失败点。

### 30—60秒口述参考

weak 是工具链和目标格式支持的弱符号机制，已参与链接的兼容强定义通常可覆盖弱定义，但前提是那个对象真的被选进最终链接。传统 GNU ld 处理静态归档通常根据扫描到该处的未解析引用抽取成员，库位置和循环依赖会影响结果。若弱默认已经满足引用，归档中的强实现可能根本未被抽取。应看最终符号和 map 引入链，再选择显式对象、锚点或受控链接策略。

### 先确认是不是同一个符号

ISR 名称大小写、C++ 名称修饰、static 内部链接、参数签名与编译条件都可能导致用户实现不是向量表引用的那个符号。用 nm 查看目标和最终 ELF，确认弱默认、用户定义与向量条目实际指向。不要只搜索源码里是否有一个看起来相同的函数，也不要把所有 weak 覆盖失败都解释成链接器优先级错误。

### 归档不是默认整体加入

静态库是对象成员的集合，链接器可能只取满足需要的成员。把库放在产生未解析引用的目标文件之前，传统一次扫描语义下可能错过后来才出现的需要；循环依赖可通过适当分组重复搜索解决，但会增加工作量。包含强覆盖实现的成员若没有触发抽取的未解析符号，单凭它“更强”并不保证进入链接。具体行为仍需核对所用链接器和选项。

### 选最小范围的修复

显式把必须生效的覆盖对象加入链接，或给该成员提供被明确引用的锚点，通常更容易审计。--whole-archive 可强制加入某段范围内全部归档成员，但可能引入无用代码、重复符号和构造副作用，使用后应及时结束该选项范围。--gc-sections 又是成员加入之后的另一层裁剪，不能把“被抽取”和“最终段保留”混成一步。

### 连续追问

**1. 两个强定义同名时怎么办？**

通常应报多重定义错误，应修正架构和构建输入，而不是默认认为后者覆盖前者。特殊链接选项可能改变行为，但把构建顺序当业务实现选择机制很脆弱。

**2. weak 是 C 标准关键字吗？**

不是。常见 GCC 使用属性，汇编器和其他编译器有各自语法及目标限制。公共可移植接口可通过小范围宏封装，但仍需验证目标格式、链接器和 LTO 下最终结果。

**3. 怎么证明修复已经生效？**

读取最终 ELF 的符号绑定、地址和向量表内容，确认处理入口落在期望实现；再在隔离板上触发对应中断验证行为。仅看到实现源文件被编译，不代表其符号被最终选中。

### 容易答错的地方

- 背“强符号总覆盖弱符号”却忽略强符号所在归档成员未被抽取。
- 为了修一个覆盖问题给所有库全程 whole-archive：可能扩大镜像并掩盖依赖设计问题。

### 动手验证

在小测试工程中做一个弱默认函数和归档内强实现，比较显式链接对象与只链接库的最终符号；查看 map 说明归档成员由哪个引用拉入。

### 查阅依据

- [GCC 14.3: Common Function Attributes](https://gcc.gnu.org/onlinedocs/gcc-14.3.0/gcc/Common-Function-Attributes.html)
- [GNU ld: Command-line Options](https://sourceware.org/binutils/docs/ld/Options.html)
- [GNU Binary Utilities: nm](https://sourceware.org/binutils/docs/binutils/nm.html)

## BUILD-07 · 开优化后变量看不见、单步乱跳，怎样调试而不误判？

方向：通用 / MCU / Linux；难度：进阶；关键词：优化、调试信息、反汇编

### 面试官可能这样问

Debug 版正常，Release 版异常。调试器说变量 optimized out，某一行被跳过，你会先关优化还是先怀疑编译器？

### 考查意图

区分合法优化与代码缺陷，理解源码行映射不等于机器执行顺序，保留可复现发布条件。

### 30—60秒口述参考

优化可内联、合并、删除无可观察影响的计算，变量也可能只在寄存器中短暂存在，源码行与指令不再一一对应。-g 提供调试信息，不表示必须关闭优化。Release 独有异常先排未初始化、越界、未定义行为、竞争和时序依赖，同时保留实际失败配置与匹配 ELF。可以用 -Og 或局部降优化辅助理解，但最后必须在原发布配置下复现并验证修复。

### 优化器改变的是实现，不是有效程序语义

若某个局部变量从未影响可观察结果，优化器可以消除它；内联后函数可能没有独立调用帧，表达式也可被常量折叠。调试器显示的源码位置来自调试映射，不是处理器按行执行的录像。单步跨多行或变量不可显示不必然是编译器错误，应结合当前 PC、寄存器和反汇编理解真实指令。

### UB 和数据竞争会放大配置差异

未初始化值在 Debug 版栈布局中碰巧是零，越界写碰巧落到闲置填充，有符号溢出检测被优化假设消除，这些都可能表现为优化后才坏。加 volatile 或全部 -O0 常改变时序和布局，却未修复根因。主机消毒器、警告和静态分析可以帮助定位，但也会改变执行条件，应保留一个与发布版尽量相近的诊断配置。

### 用可追踪的构建对照缩小范围

记录完整命令、宏、链接顺序、LTO 和库版本，确认 Debug/Release 差异不仅是优化级别。可对少量可疑文件逐步改变优化或禁用某个变换作为实验，但每步写清假设和现象，不把临时规避当成结论。若最终怀疑编译器，需在排除 UB 后构造最小可复现、固定工具链版本与目标选项，并附期望语义和实际汇编。

### 连续追问

**1. -g 会让代码变慢吗？**

调试信息主要进入镜像的调试元数据，不能简单说它必然改变运行速度；真正代码生成还受优化、帧指针和插桩等选项影响。应比较最终可执行代码，而不是凭文件变大判断时延。

**2. 加 noinline 能当正式修复吗？**

如果问题是明确的性能、栈深或调试设计需求，可以有依据地使用；如果只是让 UB 或竞争暂时消失，则不是根治。应解释它改变了什么假设，并在恢复其他优化后做回归。

**3. LTO 为什么让以前能用的符号消失？**

跨翻译单元优化能看见更多调用关系并内联或裁剪实现。硬件入口、外部约定或注册表需通过正确的可见性、引用与链接保留契约表达，不能依赖优化器过去碰巧没看见。

### 容易答错的地方

- 用调试器变量窗口证明内存中的值一定如此：变量可能被优化成常量、分片或已经不存活。
- Release 出错第一步就长期关优化：这会丢掉复现条件并可能隐藏真正缺陷。

### 动手验证

为一个小函数生成 -O0 -g、-Og -g、-O2 -g 三份汇编，比较变量和行映射；列出真实项目两种配置的全部差异，不仅优化开关。

### 查阅依据

- [GCC: Options for Debugging Your Program](https://gcc.gnu.org/onlinedocs/gcc/Debugging-Options.html)
- [GCC: Options That Control Optimization](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)
- [Clang: UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)

## BUILD-08 · 交叉编译时 ABI、浮点选项与运行库怎样保持一致？

方向：MCU / Linux；难度：进阶；关键词：交叉编译、ABI、可复现构建

### 面试官可能这样问

两个库都写着支持 ARM，为什么仍然不能链接或一运行就异常？-mcpu、-mfpu 和 -mfloat-abi 分别影响什么？

### 考查意图

理解“架构相同”不等于二进制兼容，能够固定工具链、目标、sysroot 和运行环境并验证产物。

### 30—60秒口述参考

二进制兼容不仅取决于 ARM 名字，还包括指令集、位数、端序、调用约定、数据布局、浮点参数传递和运行库。对 GCC 的 ARM 目标，-mcpu 选择处理器能力，-mfpu 说明可用浮点扩展，-mfloat-abi 影响浮点实现及调用接口；softfp 可生成硬件浮点指令但采用基础传参约定，hard 使用相应浮点 ABI。裸机与 Linux 工具链也不能仅替换前缀就混用，要核对 sysroot、启动和系统接口。

### 函数参数经过 ABI 才成为寄存器与栈

AAPCS32 规定适用 32 位 Arm 环境的参数、返回值和栈约束，但不同变体及平台补充仍需一致。一个函数在源码中都是 float f(float)，若调用者与被调用者对浮点寄存器传参约定不同，看到的值就可能不对。结构体布局选项、枚举大小和额外打包设置也能造成跨模块失配；头文件文字相同并不保证两边编译配置相同。

### 目标能力、运行库与设备初始化配合

给没有对应 FPU 的芯片生成浮点指令会失败；芯片有 FPU 也需启动代码按架构启用和管理上下文。裸机工具链通常配套启动文件和面向裸机的 C 库接口，Linux 用户态则依赖加载器、系统 ABI 与目标库。误用主机头文件或库路径会产生更隐蔽的不匹配，交叉构建应显式固定工具链文件、sysroot 和搜索路径。

### 可复现意味着能解释每一个输入

记录源码版本、子模块、编译器和链接器版本、完整参数、链接脚本、生成配置与库归档。检查 ELF 头和 ARM 属性、反汇编指令及库的构建说明，而不是只看文件扩展名。持续构建使用独立输出目录，避免不同目标共用旧对象；对最终镜像保存哈希和匹配调试符号。完全字节一致还涉及时间戳、路径等元数据，需要另行控制，不应把“能再次编译”当作强可复现。

### 连续追问

**1. soft 与 softfp 一定能随便混吗？**

它们通常使用基础浮点传参约定，但仍要满足指令集、库选择、其他 ABI 和运行环境兼容。softfp 对硬件浮点指令的需求不能被忽略；具体链接器属性检查和工具链 multilib 选择也需核对。

**2. 能用 x86 主机编译的库放到 ARM 上吗？**

普通机器码库不能，因为指令集与 ABI 不同。源码可重新交叉编译，某些中间表示也需匹配工具链机制；不能把同名 C API 当成二进制可移植承诺。

**3. 头文件匹配但运行库不同会怎样？**

结构布局、符号版本、分配器、异常处理或线程局部存储约定可能不同。应使用与目标 sysroot 配套的头和库，并避免跨不兼容运行库分配释放；实际是否兼容要有供应商或 ABI 依据。

### 容易答错的地方

- 把 softfp 解释为纯软件浮点：它可使用硬件指令，但调用接口与 hard 不同。
- 只保存源码不保存工具链与链接脚本：之后可能无法重建现场地址对应的镜像。

### 动手验证

读取两个 ARM 库的 ELF 属性和构建参数，列出至少五项兼容性检查；为一个小项目记录一次完整构建清单，再用独立输出目录重建比较结果。
